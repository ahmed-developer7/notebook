Section 1. Why it matters.

rest is the lingua franca of web A P Is. Despite graph Q L, G R P C, and event-driven challengers, it remains the default for public and internal H T T P A P Is. Why? Because H T T P is universal, every client knows it, every cache understands it, every gateway can route it.
The deep-dive (A P Is and Microservices) covers A S P dot NET Core's ApiController + Minimal A P Is mechanics. this session covers the rest theory the deep-dive doesn't dwell on, Richardson Maturity, HATEOAS, content negotiation, idempotency contracts.

For real-time server to client push (notifications, L L M token streaming, live dashboards), see Server-Sent Events, the dot NET 10 native S S E pattern. For client-specific aggregation back-ends, see B F F and Aggregation.

Why interviewers ask: "design a rest A P I for X" is the most common system-design warm-up. They're testing whether you understand the discipline beyond [HttpGet] annotations, resource modeling, status code semantics, idempotency guarantees, hypermedia, versioning strategy.

Section 2. Core concepts (chapter extensions).

-- pause --
Richardson Maturity Model.

A 4-level scale (0, 3) measuring how "RESTful" an A P I is. Most A P Is called "rest" are level 2.

Level 0, The swamp of POX: one URI, one H T T P verb (POST), all operations tunneled through the body. soap-over-H T T P lives here.
Level 1, Resources: different URIs for different things ( /orders or 42, /customers or 7 ), but still one verb.
Level 2, H T T P verbs: correct verb for the operation ( GET /orders or 42, POST /orders, PUT /orders or 42, DELETE /orders or 42 ). Status codes match semantics (200, 201, 204, 404, 409). This is where most A P Is stop.
Level 3, Hypermedia (HATEOAS): responses contain links to related resources and next legal actions. Client follows links rather than constructing URIs.

In production, Level 2 is the pragmatic target. Level 3 is rare, most clients are coupled to URI templates anyway, and HATEOAS adds payload weight without proportional benefit unless you're building a true hypermedia A P I (for example, a public, evolving, third-party-consumed A P I).

Content negotiation.

The client tells the server what format it wants via Accept; the server tells the client what it produced via Content-Type. A S P dot NET Core handles this automatically when you use ObjectResult / Ok(value), the response is Jason by default, X M L if the client asks.

Custom formatters (Protobuf, MessagePack, CSV): implement OutputFormatter and register. The framework picks the best match based on Accept.

Content negotiation is an M V C feature, not a Minimal A P I one.

Everything in the section is true of controllers. Almost none of it is true of Minimal A P Is, and the gap catches people out because the two styles sit in the same Program.cs.

The mechanism is the tell. Microsoft's own formatting documentation says content negotiation is implemented by ObjectResult.
When a controller action returns a POCO, or Ok(value), the runtime wraps it in an ObjectResult, walks the media types in the client's Accept header in preference order, and picks the first registered output formatter that can produce one of them.
AddXmlSerializerFormatters() and any custom OutputFormatter you write join that list. That list is the negotiation.

Minimal A P I results never enter that pipeline. Results.Ok(value) and TypedResults.Ok(value) return IResult implementations that write the response themselves, the documented behaviour for a returned object is that the framework Jason-serialises it and sets Content-Type: application or json.
There is no formatter list to consult, so there is nothing for Accept to select from. A Minimal A P I endpoint returns Jason to a client asking for X M L, and nothing in the app is misconfigured.

Two consequences worth being able to state. Registering AddXmlSerializerFormatters() has no effect on a MapGet endpoint, it configures M V C's formatter collection, which that endpoint does not use.
And the M V C knobs around negotiation have no Minimal A P I counterpart: MvcOptions.ReturnHttpNotAcceptable (return 406 Not Acceptable instead of falling back to the default format when nothing matches) and MvcOptions.RespectBrowserAcceptHeader (stop ignoring Accept: /;
it is false by default) are both M V C-only.
If a Minimal A P I genuinely needs two representations, you read Accept in the handler and return an explicit content type, or you keep those endpoints in controllers.

In the real world: A partner integration demands X M L. The team calls AddXmlSerializerFormatters(), verifies it against the controller-based /v1 or reports endpoint, and ships. The newer /v2 or reports endpoint, written as a Minimal A P I, keeps returning Jason whatever the partner sends.
Hours go into the cores config, the gateway and the serializer options before someone notices the two endpoints are in different response pipelines.

-- pause --
Collection endpoints beyond pagination.

A collection endpoint is where rest design gets expensive, because everything a client wants to do to a set, filter it, sort it, trim the fields, walk through it, has to be expressed in a query string that you then translate into a query plan.

Filtering. Fixed named parameters ( ?status set to pending and customer Id set to 7 ) are boring and safe: each one maps to a column you have chosen to index, and anything you did not name is rejected.
Expression languages, OData's $filter, or a home-grown ?filter= grammar, move the query plan to the caller, so any client can now write a predicate over an unindexed column and you inherit their table scan.
If you adopt one, constrain it: an allow-list of filterable fields, and a required filter that hits an index.

Sorting. ?sort=-created At,name, with a leading minus for descending, is the common shape. The thing to be able to say in an interview is that the sort key has to be part of the index that satisfies the filter; otherwise every page sorts the whole filtered set before discarding almost all of it.

Sparse fieldsets. ?fields set to id,status,total lets a mobile list view avoid downloading a fat DTO. Jason:A P I specifies this as fields[type]=..
The cost is that your response shape is no longer static, so the OpenAPI schema and any generated client degrade to "some subset of these properties", and your cache keys multiply.

Cursor stability. Offset pagination is not stable when the set changes underneath it. Insert a row before your offset between page three and page four and one record shifts across the boundary and is never returned; delete one and a record is returned twice.
Keyset (cursor) pagination encodes the last-seen sort key instead of a count, so the position is defined by data rather than by how many rows currently precede it, stable under both insert and delete.
It is also cheaper at depth: OFFSET 200000 makes the database produce and discard two hundred thousand rows, whereas a keyset predicate seeks straight into the index.

Ranges are a different problem.
RFC 9110 Section 14 defines range requests, Accept-Ranges advertises support, Range asks for a byte span, Content-Range describes what came back, and Section 15 defines the two status codes that go with them: 206 Partial Content on success, 416 Range Not Satisfiable for an impossible range.
That is for one large representation, a video, an export, a resumable download, not for paging a collection.
In A S P dot NET Core you get the whole dance by passing enableRangeProcessing: true to the file result helpers; add an entity tag and the client's If-Range header makes the resumption conditional, so an interrupted download only resumes if the file has not changed.

In the real world: An admin screen lists orders newest-first behind an offset pager. Support reports that the daily reconciliation "skips orders", but only during busy hours.
There is no bug in the query: new orders arriving between page requests push older rows down, so the row that was at position 200 becomes 201 and is never returned by page five.
Moving to a keyset cursor on (created At, id) removes the entire class of defect, and the extra row trick removes the COUNT(*) at the same time.

Idempotency in H T T P verbs.

Idempotent = calling once and calling N times has the same effect on server state. This is the contract clients (and proxies, and retry middleware) rely on.

GET, Yes, Yes, Read.
HEAD, Yes, Yes, Read headers only.
OPTIONS, Yes, Yes, Discoverability / cores preflight.
PUT, Yes, No, Replace (full update).
DELETE, Yes, No, Remove.
POST, No, No, Create (each call creates new).
PATCH, Depends, No, Partial update, idempotent if RFC 7396 (merge), not if RFC 6902 (ops).

POST is not idempotent, POSTing the same order body twice creates two orders. To make POST safe to retry, use the Idempotency-Key header pattern:

The server stores the key for 24 hours; if the same key arrives again, it returns the original response without re-processing. Stripe popularized this pattern; it's now widely used.

-- pause --
Making Idempotency-Key safe under concurrency.

The version, and the version in this session's walkthrough, is check-then-act, and it does not survive the failure it was invented for. A cellular handover produces two identical requests carrying the same key, arriving milliseconds apart, quite possibly on two different instances.
Both look the key up, both miss, both create the order. The lookup is not the protection; it only narrows the window.

The fix is to make the reservation atomic. Insert the key first, into a table with a unique constraint on it, in the same transaction that performs the side effect. Then there are exactly two outcomes.
If the insert succeeds, you own the key: do the work, store the response body and status code alongside the key, commit both together.
If the insert fails on the unique violation, someone else owns it: load the row, and either replay the stored response or tell the client the original is still running. The database's unique index is doing the concurrency control, which is the only component in the picture that can.

Three contract details make the pattern correct rather than merely plausible, and the IETF has written most of them down in draft-ietf-httpapi-idempotency-key-header, "The Idempotency-Key H T T P Header Field", an Internet-Draft that expired without ever becoming an RFC.
Cite it as the shape the industry converged on, not as a standard you comply with.

Retry while the original is in flight. The draft says a resource SHOULD reply 409 Conflict when a request is retried while the original is still being processed.
That is a real state you have to represent, the key row exists but has no response yet, and a client that gets 409 knows to wait rather than to give up.
Same key, different body. The draft says the server SHOULD reply 422 when a key is reused with a different request payload, and describes an idempotency fingerprint, for example a checksum of the request payload, stored with the key so the mismatch is detectable at all.
Without a fingerprint, a client that accidentally reuses a key silently receives a completely different order.
Scope the key to the caller. The key is client-generated, so it is not globally unique. Store it under (tenant or A P I key or user) plus the key, or one customer's UUID collision hands them another customer's order.

And one thing this session currently contradicts itself on: the replay must return the original status, 201 Created with its Location header, not 200 OK. A client that branches on 201 to read Location breaks the moment a retry downgrades it.

In the real world: A payments team ships idempotency keys and still sees duplicate charges, but only during incidents, because that is exactly when retries pile up and two replays genuinely race. The lookup passes every unit test, because unit tests do not run two requests at once.
The fix is one unique index on (tenant_id, idempotency_key) and an insert-first flow; nothing changes on the client.

Problem Details, the error body rest forgot.

Every drill in this session argues about which status code to return, and none of them says what goes in the body. The standard answer is RFC 9457, "Problem Details for H T T P A P Is", and note the number, because it obsoleted RFC 7807 in 2023 and 7807 is the one most candidates still quote.

The contract is small.
The response carries the media type application or problem+json (there is an X M L variant, application or problem+xml ) and a Jason object with five defined members: type, a URI reference identifying the kind of problem; status, the H T T P status code repeated in the body;
title, a short human-readable summary of the type that should not vary between occurrences; detail, an explanation of this occurrence; and instance, a URI identifying this specific occurrence.
Anything else you add is an extension member, that is where a correlation id, a field-level error list or a retry hint belongs.

Two things RFC 9457 added over 7807 are worth knowing, because they are the level of detail that distinguishes having read it from having heard of it. It creates an IANA "H T T P Problem Types" registry so widely-reused problem types can be shared rather than reinvented per A P I.
And it registers about:blank as the type meaning "no semantics beyond the status code", so if you have nothing meaningful to point type at, about:blank is the correct value, not an invented documentation URL that 404 seconds.

The dot NET wiring is a handful of members that are easy to name precisely:

builder.Services.AddProblemDetails() registers the default IProblemDetailsService.
On its own it changes nothing; what it does is let three pieces of middleware emit problem details for error responses that do not already have a body, ExceptionHandlerMiddleware, StatusCodePagesMiddleware and DeveloperExceptionPageMiddleware.
So the working pairing is AddProblemDetails() plus app.UseExceptionHandler() and app.UseStatusCodePages().
The default writer only speaks Jason: application or json, application or problem+json, and the wildcards. A client sending Accept: application or xml falls through to whatever fallback you wrote, which is a reason to write one, via IProblemDetailsService.TryWriteAsync returning false.
To stamp a field onto every problem, a trace id, almost always, set ProblemDetailsOptions.CustomizeProblemDetails in the AddProblemDetails callback.
For per-exception-type handling, implement IExceptionHandler (one method, TryHandleAsync, returning ValueTask ) and register it with builder.Services.AddExceptionHandler(). Handlers run in registration order until one returns true.
They are singletons, so resolve scoped dependencies from HttpContext.RequestServices.
To emit one deliberately: TypedResults.Problem(.) / Results.Problem(.) in Minimal A P Is; ControllerBase.Problem() and ControllerBase.ValidationProblem() in controllers.
M V C model-validation failures produce ValidationProblemDetails, which is problem details plus an errors dictionary keyed by field name, the shape a form-driven client actually needs.

In the real world: On-call gets paged for a spike in 4xx. The A P I returns bare status codes with empty bodies, so every support ticket begins with "can you send me the exact request you made?" and the customer cannot, because their S D K swallowed it.
Adding problem details with a trace Id extension member turns that into: the customer pastes the response, the engineer pastes the trace id into the APM, and the reproduction step disappears entirely.

PATCH, the two media types, and shipping it in dot NET.

this session says four times that RFC 7396 merge patch is idempotent and RFC 6902 Jason Patch is not. What it never says is how the server knows which one it is holding. The answer is the Content-Type header, not the shape of the Jason, and that is the detail an interviewer probes for.

Merge patch, RFC 7396, uses application or merge-patch+json. The document looks like the resource with only the members you want changed, and null means "remove this member".
Which is why merge patch cannot set a field to null, and cannot address a single array element, an array in the patch replaces the whole array.

Jason Patch, RFC 6902, uses application or json-patch+json. The document is an ordered array of operations, add, remove, replace, move, copy, test, each addressing a Jason Pointer path.
It can append to an array, which is precisely why it is not idempotent, and it has test, which gives you a conditional patch without a separate header.

In dot NET, A S P dot NET Core's in-the-box patch support is Jason Patch.
Historically it required the Microsoft.AspNetCore.Mvc.NewtonsoftJson package and AddNewtonsoftJson(), which replaces the System.Text.Json input and output formatters for all Jason,
not only for patch, hence the long-standing workaround of registering just NewtonsoftJsonPatchInputFormatter at the front of MvcOptions.InputFormatters and leaving every other formatter untouched.
From dot NET 10 there is a System.Text.Json implementation in the Microsoft.AspNetCore.JsonPatch.SystemTextJson package, giving you JsonPatchDocument and ApplyTo(object) without the Newtonsoft dependency.
Microsoft's documentation is explicit that it is not a drop-in replacement: it does not support dynamic types such as ExpandoObject, and ApplyTo selects properties from the runtime type of the target rather than the declared type.

Three operational details that bite:

ApplyTo mutates the target in place and does not roll back. If operation four fails, operations one to three have already been applied to your entity. Apply to a copy, or apply before the object is attached to the change tracker.
The request must carry Content-Type: application or json-patch+json. In a Minimal A P I you declare that with .Accepts>("application or json-patch+json") so it appears correctly in the OpenAPI document instead of being described as plain Jason.
The docs state plainly that the security risks are inherent to the Jason Patch standard and that the A S P dot NET Core implementation does not attempt to mitigate them, validating the size and structure of the incoming document before calling ApplyTo is your job.

Merge patch has no equivalent binder in the box; you read the body yourself, as a JsonNode or as a DTO of nullable properties, and apply the members that are present.
Which is why a great many dot NET A P Is quietly accept application or json on PATCH and implement merge semantics by hand, defensible, as long as you know that is what you have done and can say so.

In the real world: A team exposes PATCH /users/{id} bound to JsonPatchDocument, where User is the EF entity. A client sends [{"op":"replace","path":"/is Admin","value":true}] and it works, because a patch document can reach any property on the type it is bound to.
The fix is the same fix as for over-posting, and it is the subject of the next section.

Object-level authorisation and the binding surface.

Authentication tells you who is calling. It does not tell you whether this caller may touch this row, and that gap is item one on the OWASP A P I Security Top 10: API1:2023, Broken Object Level Authorization.
The shape is always identical, the endpoint takes an id from the path, loads the object by that id, returns it. Customer 7 edits /orders or 42 to /orders or 43 and reads someone else's order. Older material calls it IDOR, insecure direct object reference; same defect.

The rest-design fix is not a permission check bolted on after the load. It is to put the ownership into the query. Load by (customer, id) or (tenant, id) rather than by id, so a row that is not theirs simply does not exist.
A forgotten check then produces a missing row rather than a leak, and the natural response is 404 rather than 403, which has the side benefit of not confirming to an attacker that order 43 exists.
Swapping sequential integers for GUIDs raises the cost of enumeration and changes nothing about the missing check; opaque identifiers are defence in depth, not the defence.

The write side is API3:2023, Broken Object Property Level Authorization, the 2023 edition's merge of what used to be listed separately as Excessive Data Exposure and Mass Assignment, on the grounds that both are the same root cause at the property level.
Binding a request body straight onto an entity hands the client the entity's entire property surface: POST /users carrying {"email":". ","is Admin":true} sets IsAdmin, because a model binder has no idea which properties were meant to be client-controlled.
The mirror image is returning the entity, which ships PasswordHash and InternalNotes to anyone who asks. OWASP's own guidance is to avoid functions that automatically bind client input onto internal objects and to allow changes only to properties the client should be able to update.

this session already recommends DTOs, but purely as a coupling and versioning concern. The security argument is the stronger one and the one to give under cross-examination: a request DTO is an allow-list of what the client may set, and a response DTO is an allow-list of what the client may see.
A property you did not put on the DTO cannot be reached, by construction, regardless of what the client sends. That extends to PATCH, bind JsonPatchDocument, never JsonPatchDocument.

Full authentication and authorisation mechanics live in Authentication and Authorization; the slice that belongs to A P I design is the two, scope the query, and control the binding surface.

In the real world: An audit finds a mobile "update profile" endpoint binding the full user entity. Nobody had exploited it. What made it indefensible was the timeline: the entity had grown a Roles collection two sprints earlier, when a different team added admin support.
The endpoint's attack surface expanded silently, because it was defined by a class somebody else owned. No coupling argument for DTOs is ever that persuasive.

cores with credentials, and the headers the browser hides from you.

Drill 7 covers when the browser preflights. Two further pieces of cores bite rest A P Is specifically, and neither is about preflight at all.

Credentials. A browser does not attach cookies or H T T P authentication to a cross-origin request unless the calling code asks for it, credentials: 'include' on fetch, or with Credentials on XMLHttpRequest.
Once it does, the server must answer with Access-Control-Allow-Credentials, which in A S P dot NET Core comes from AllowCredentials() on the policy.
If that header is missing, the browser refuses to expose the response to the calling script and the request fails, the response arrived, the script just never sees it.

The trap is the interaction with the wildcard. The cores specification says an origin of * is invalid when Access-Control-Allow-Credentials is present, so AllowAnyOrigin() and AllowCredentials() cannot be combined.
Microsoft's docs are blunt about it: specifying both is an insecure configuration that can result in cross-site request forgery, and the cores service deliberately returns an invalid cores response when it sees both.
The correct shape is WithOrigins(.) naming real origins, which is also why a credentialed A P I must echo Vary: Origin, the point Drill 7 makes about shared caches.

Exposed headers, and this one matters more than its obscurity suggests. By default a browser only lets script read the seven cores-safelisted response headers: Cache-Control, Content-Language, Content-Length, Content-Type, Expires, Last-Modified and Pragma.
Everything else is present on the wire and invisible to the page. Now look at what this chapter has been recommending: Location on a 201, ETag for conditional requests, Retry-After on a 429, Link for pagination.
Not one of those is readable by a browser client cross-origin unless the server lists it via WithExposedHeaders(.), which emits Access-Control-Expose-Headers.
A perfectly correct rest A P I can therefore look broken to a single-page app, the 201 has a Location header, and response headers get('Location') returns null.

In the real world: The most familiar bug report in web development is "it works in Postman, it fails in the browser". Postman is not a browser: it does not enforce the same-origin policy, does not preflight, and does not hide response headers.
So the A P I is genuinely correct and the client is genuinely broken, and the two teams argue past each other for a day. The tell is in the browser console rather than in the server logs, because the server returned 200 and considers the matter closed.
The second-most familiar version of the same bug is the pagination cursor that "the A P I isn't sending", it is sending it, in a Link header the browser will not let the script read.

Rate limiting, 429, Retry-After, and the dot NET middleware.

429 Too Many Requests says this client exceeded its quota, so it should slow down and carry on. 503 Service Unavailable says the server is in trouble, which is everyone's problem.
Getting them the wrong way round misdirects every retry policy downstream: a client seeing 503 may fail over to another region or trip a circuit breaker; a client seeing 429 should simply back off.

Either one is close to useless without Retry-After. RFC 9110 Section 10.2.3 defines it, and its value is either a number of seconds or an H T T P date.
Without it every client invents its own backoff, so the polite ones wait far too long and the aggressive ones retry immediately and keep you saturated.
Retry-After is also the missing half of Drill 10's 202-plus-polling loop: it is how you tell a poller when to come back, rather than leaving it to guess.

If you want to publish the quota rather than only the rejection, the IETF HTTPAPI working group has draft-ietf-httpapi-ratelimit-headers, "RateLimit header fields for H T T P", defining RateLimit (quota currently available) and RateLimit-Policy (the policy the server advertises).
It is still an Internet-Draft, not an RFC, name it as the direction of travel, not as something you claim compliance with.

In dot NET, Microsoft.AspNetCore.RateLimiting gives you the middleware: builder.Services.AddRateLimiter(.) plus app.UseRateLimiter(), with four algorithms, AddFixedWindowLimiter, AddSlidingWindowLimiter, AddTokenBucketLimiter, AddConcurrencyLimiter.
The first three cap requests per unit of time; the concurrency limiter caps requests in flight and is the right choice for an endpoint whose cost is a slow downstream call rather than a burst of cheap ones.

Three things teams get wrong:

Partitioning. A single global counter means one noisy client starves everybody. PartitionedRateLimiter.Create lets you key the bucket by user identity, A P I key or address.
Microsoft's docs carry the warning worth repeating back in an interview: partitioning on client IP makes you vulnerable to source-address spoofing, because every spoofed address creates a fresh partition with a fresh allowance.
The rejection response is your job. RateLimiterOptions.RejectionStatusCode sets the code and nothing else. To send a useful response, set RateLimiterOptions.OnRejected; the lease exposes the wait hint through MetadataName.RetryAfter, which is where the value for the Retry-After header comes from.
Middleware order. UseRateLimiter must come after UseRouting when you use endpoint-specific policies ( RequireRateLimiting("name") or [EnableRateLimiting] ), because the endpoint has to be selected before its policy can be found. Global limiters alone can go earlier.

And the caveat that separates a good answer from a complete one: this middleware is in-process. Each instance keeps its own counters, so behind four replicas your advertised "100 per minute" is enforced as up to 400. It is a per-node load-shedding guard, not a billing meter.
A contractual quota belongs at the gateway or in a shared store.

In the real world: An A P I advertises 1,000 requests per hour and enforces it with the in-process fixed-window limiter behind an autoscaler. Customers report that the limit is looser at peak, and they are right, because peak means more instances, and each instance carries its own counter.
The team keeps the in-process limiter as a safety valve and moves the contractual quota to the gateway, which is the only place that sees every request.

Caching in A S P dot NET Core, where the ETag actually comes from.

Drills 6 and 12 describe the H T T P caching contract: ETags, conditional requests, Cache-Control, Vary. That is what clients and intermediaries do with your response. Separately, A S P dot NET Core can cache the response on the server, and the two live in completely different places in Program.cs.

There are two middlewares and the distinction is a fair interview question. Response caching is the older one: an H T T P cache inside your process, driven by cache headers, which among other conditions will not store a response to a request carrying an Authorization header.
Output caching, added in dot NET 7, is a server-side cache you control explicitly rather than through headers, builder.Services.AddOutputCache() and app.UseOutputCache(), then CacheOutput() on a Minimal A P I endpoint or [OutputCache] on an action.

Output caching's defaults are conservative and worth memorising, because they are what someone will ask you: only 200 responses, only GET and HEAD, nothing that sets a cookie, and nothing for authenticated requests.
Policies configured through AddBasePolicy and AddPolicy set expiry, one minute if you do not say, and vary rules through SetVaryByQuery, SetVaryByHeader and VaryByValue.
Middleware order matters and the docs are specific: UseOutputCache goes after UseCors, after UseRouting, and after UseAuthentication / UseAuthorization, put it earlier and it can serve content cached for one user to another.

The feature that earns output caching its place in an A P I is eviction by tag. Tag an endpoint with CacheOutput(b goes to b.Tag("catalogue")), then call IOutputCacheStore.EvictByTagAsync("catalogue", ct) from wherever the write happens.
That turns a cache from "wait for the T T L" into "invalidate when the data changes", which is what you actually want for something read constantly and written occasionally.
Two limits to state honestly: the default store is in-memory and per-process, so each instance has its own cache, loses it on restart,
and an eviction on one node does not evict on the others, the documented shared option is Microsoft.AspNetCore.OutputCaching.StackExchangeRedis with AddStackExchangeRedisOutputCache, and IDistributedCache is explicitly not recommended here because it lacks the atomic operations tagging needs.
Resource locking is on by default, so a miss on a hot key does not send every concurrent request to the origin; SetLocking(false) turns that stampede protection off.

Which leaves the question Drill 6 opens and never closes: where does the ETag value come from? Drill 6 already connects If-Match and 412 down to E F Core's RowVersion, and that connection is the answer running the other way too. There are two implementations with different costs.
Hash the serialised representation, correct by construction, because the tag changes exactly when the bytes change, but you have to build the whole response before you can compute the tag, so you save bandwidth and not work.
Project a version column, use the row's RowVersion (or xmin, or updated_at ) as the tag, so a single-column read tells you whether to do the rest of the work at all, saving the query and the serialisation.
That second one is a weak validator in the H T T P sense: the bytes could differ while the version matches, or the version could move without a semantically meaningful change. Which is exactly what W/". " is for, and why Drill 6's strong-versus-weak distinction is not academic.

Usefully, revalidation is free once output caching is on: if your handler sets ETag and the client sends If-None-Match, the middleware returns 304 from a fresh cache entry with no extra configuration.

In the real world: A product catalogue endpoint is cached for five minutes. Merchandising corrects a price and rings support because the change "isn't live".
Tagging the endpoint and calling EvictByTagAsync from the price-update handler turns a five-minute complaint into an instant one, and immediately surfaces the next problem, which is that eviction only clears the node that handled the POST until the store is shared.

Endpoint metadata, TypedResults, result unions, and generated links.

Everything is about behaviour. This is about what your endpoint declares, which is what OpenAPI generation, generated clients and the compiler all read.

Minimal A P Is ship two result helpers. Results returns IResult, an interface, so the framework learns nothing about what the endpoint produces, and you have to describe it separately with .Produces().
TypedResults returns the concrete implementation types from Microsoft.AspNetCore.Http.HttpResults, Ok, NotFound, Created, and those carry their own metadata, so the description is derived from the signature rather than maintained beside it.

The catch is that a handler returning two different concrete types will not compile, because the compiler will not infer a common type across the branches. That is what the union types exist for.
Declare the return as Results, NotFound> and two things happen: the branches compile, and returning a type not listed in the generic arguments becomes a compilation error.
The metadata cannot drift from the code, which is the entire point, and it is a genuinely better answer than "we keep the .Produces attributes up to date".

Two habits follow. First, name endpoints with .WithName("GetOrder") and generate URLs from the name with LinkGenerator, GetPathByName(http Context, "GetOrder", new { id }), rather than interpolating strings.
this session recommends LinkGenerator for HATEOAS links and then hardcodes $"/orders/{order.Id}" in its own Created call; change the route prefix and the Location header silently points at nothing.
Named routes plus LinkGenerator is one mechanism serving both the Location header and any _links object.
Second, declare error responses too: .ProducesProblem(StatusCodes.Status409Conflict) and .ProducesValidationProblem() (which defaults to 400 and application or problem+json ), or your generated spec claims the endpoint only ever succeeds and every client generator will believe it.

The documentation-tooling half of this story, generating and serving the OpenAPI document itself, belongs to A P I Documentation. This section stops at the metadata your endpoint emits.

In the real world: A front-end team generates a TypeScript client from the OpenAPI document and finds every method typed as returning Order, including the ones that 404, because the handlers return IResult and nobody wrote .Produces.
Error handling degrades into catching exceptions and matching on message strings. Rewriting the handlers as Results, NotFound> regenerates a client that models both outcomes, and three "the A P I lies about its shape" bugs become compile errors.

-- pause --
Statelessness under cross-examination.

Statelessness means each request carries everything needed to process it, and the server keeps no per-client conversational state between requests. It does not mean the server keeps no state. Your database is state.
The real test is narrower: does request N plus one depend on the same server instance having handled request N?

Three things break it in practice. Sticky sessions are an admission that a request cannot be served by any instance; affinity works until an instance is drained during a deploy and every user pinned to it loses whatever was in its memory.
Server-side cursors, an endpoint that hands back a handle and then serves "the next page of that handle" from an in-memory result set, have moved the client's position onto one node, which is precisely why keyset pagination encodes the position in the cursor the client carries.
In-memory caches used as truth are fine as an optimisation and a violation the moment correctness depends on hitting the same node; the output cache is the honest version, where a miss elsewhere costs a slow request rather than a wrong answer.

Then the cross-question this session sets up and never answers. Its own idempotency fix stores a per-client key on the server for 24 hours. Is that stateful?

No, provided the store is shared and the key travels in the request. The client sends Idempotency-Key on every retry, so the request is still self-describing; the server is looking that key up in a durable store exactly as it looks up an order.
It becomes a violation the moment the store is a per-instance in-memory dictionary, because then the retry has to land on the same node to be recognised, which is the property statelessness was supposed to eliminate.
The same test applies to rate-limit counters and output-cache entries: shared store, fine; per-node memory, you have quietly reintroduced affinity. And the failure will not show up as an error, it will show up as duplicate orders during a deploy.

In the real world: An idempotency layer built on IMemoryCache passes every test, because tests run against one instance, and works most of the time in production, because retries usually land on the same node behind a keep-alive connection.
The duplicates appear during deploys, when connections are redistributed across a changing pool. The logic is correct; the bug is where the logic keeps its memory.

-- pause --
H T T P or 2, H T T P or 3, and what actually changes for rest.

H T T P or 2 is RFC 9113, which obsoleted RFC 7540. H T T P or 3 is RFC 9114, running over QUIC, RFC 9000. The semantics are identical in all three, the methods, status codes and header fields of RFC 9110 do not change one bit. What changes is the wire format, and therefore what is cheap.

H T T P or 2 multiplexes many concurrent requests over a single connection, which retires a generation of workarounds: domain sharding, sprite sheets, and batch endpoints invented purely to save round-trips.
It also compresses headers (HPACK, RFC 7541), which matters more for A P Is than people expect, because a rest request is mostly headers, a bearer token repeated across a thousand requests compresses away.

Now the correction this session needs, because Drill 8 and Drill 11 both lean on it. H T T P or 2 removes head-of-line blocking at the application layer, between streams. It does not remove it at the transport layer.
Those streams share one TCP connection, and TCP delivers bytes in order, so a single lost segment stalls every stream on that connection until it is retransmitted. That is not a footnote, it is the entire reason QUIC exists.
QUIC runs over UDP and tracks loss per stream, so a lost packet stalls only its own stream, and QPACK (RFC 9204) is HPACK redesigned so that header compression itself does not reintroduce the blocking QUIC just removed.

The other H T T P or 3 property worth knowing for mobile clients is connection migration: a QUIC connection is identified by a connection ID rather than by the four-tuple of addresses and ports, so a handset moving from Wi-Fi to cellular keeps the connection instead of re-handshaking.
Which is, as it happens, the same handover that produced this session's duplicate-order incident.

In dot NET, Kestrel supports H T T P or 3, enabled per endpoint with HttpProtocols.Http1AndHttp2AndHttp3, Microsoft's guidance is to configure it alongside 1.1 and 2, because not every router, firewall and proxy handles H T T P or 3.
Discovery is by advertisement rather than negotiation: the first request arrives over H T T P or 1.1 or H T T P or 2, Kestrel adds an Alt-Svc header announcing that H T T P or 3 is available, and the client may switch for subsequent connections.
ListenOptions.DisableAltSvcHeader suppresses the advertisement.

What this means for design, plainly:
chattiness is cheaper than it was, so "we need a batch endpoint to save round-trips" is a weaker argument than it used to be, though not a dead one, because each request still costs a trip through your middleware, a log line and a unit of server work regardless of how it arrived.
And none of it changes the rest contract. If your A P I design discussion has become an argument about the transport, it has stopped being a rest design question.

In the real world: A team migrates a mobile flow to H T T P or 2 and reports a large latency improvement.
Digging in, most of the win came from holding one warm connection rather than from multiplexing at all, the previous client opened a fresh T L S connection per request because of a misconfigured handler.
Worth knowing, because it is the usual shape of these stories: a good share of "H T T P or 2 made it faster" is really "we stopped paying for handshakes", and an interviewer who has measured it will expect you to separate the two.

Section 3. Common pitfalls.

Verbs in URLs. /get Orders, /create User, that's R P C, not rest. Resource is the noun; verb is the H T T P method.
Wrong status code. Returning 200 OK with {"error": "."} body for failures defeats every retry middleware and H T T P cache. Use the right 4xx or 5xx code.
POST for everything. Treating POST /update User like a remote procedure call. Use PUT / PATCH so caches and retries behave correctly.
Non-idempotent PUT. PUT must replace; calling it twice with the same body must produce the same state. If your PUT increments a counter, it's broken.
No version strategy. When the A P I changes shape, clients break. Pick one (URI: /v2 or orders, header: Accept-Version: 2 ) and document it. See A P I Versioning.
Returning entities directly. Coupling DB schema to A P I shape means schema changes break clients. Use DTOs.
Inconsistent pagination. ?page set to 1 versus ?offset set to 0 and limit set to 50 versus cursor-based. Pick one per A P I and document.
Sensitive data in URLs. URLs end up in server logs, browser history, proxy logs. Put secrets in headers or body, never query strings.
No Content-Type / Accept headers in clients. Default to Jason in your client and the server defaults will accept. Don't rely on luck.
Returning H T T P 200 for "not found". Return 404 so clients can distinguish "doesn't exist" from "exists but empty."

Section 4. Interview-ready summary.

rest = H T T P verbs + resource URIs + status codes + stateless requests.
Verbs: GET (read, idempotent), POST (create, NOT idempotent), PUT (replace, idempotent), PATCH (partial), DELETE (idempotent).
Status codes: know 200 or 201 or 204 or 400 or 401 or 403 or 404 or 409 or 422 or 429 or 500.
Richardson Maturity: most A P Is at level 2 (verbs+codes); level 3 (HATEOAS) rare in practice.
Idempotency-Key header: the standard pattern for safe POST retries.

Expected interview questions:

"Design a rest A P I for an e-commerce orders system.", Resource modeling: /orders, /orders/{id}, /orders/{id}/items, /orders/{id}/cancel. Verbs and status codes. Error responses with Problem Details.
"What's the difference between PUT and PATCH?", PUT replaces the entire resource (idempotent). PATCH partially updates (idempotent only with merge semantics, not ops semantics).
"How do you make a POST safe to retry?", Client sends Idempotency-Key header with a UUID. Server stores the key + response for 24 hours. Duplicate keys return the original response.
"Why is rest stateless?", Each request contains all the info needed to process it. No server-side session state per client. Enables horizontal scaling and caching.
"What status code for a duplicate-key insert?", 409 Conflict (semantic state conflict) or 422 Unprocessable Content (depending on your conventions). Not 400.
"rest versus G R P C versus graph Q L, when do you pick which?", rest: public A P Is, browser clients, caching matters. G R P C: service-to-service, low-latency, strong typing. graph Q L: B F F / aggregating multiple sources, client-driven shape.
"What is HATEOAS?", Hypermedia as the engine of application state, responses include links to next legal actions. Theoretically pure rest; in practice rare.

Section 5. Interview Cross-Questioning Drill.

Honest caveat: reading this section once doesn't make you interview-ready. Cover the answers, write them cold, then check. Pair with a senior for live mock cross-questioning. The guide removes "I never thought about that" surprises; mock interviews convert knowledge into reflex. Both are needed.

Each drill is Q to A to Cross-Q to A to Cross-Q² to A. Practice answering the cross-questions without re-reading. If you stumble on any cross-Q², go re-read the relevant section.

-- pause --
Drill 1, PUT versus PATCH versus POST.

Q: I have an "update user email" endpoint. PUT, PATCH, or POST?-- think --

A: PATCH is the right answer when you're changing a subset of fields on an existing resource. PUT requires the client to send the entire resource representation (full replacement). POST is for creating new resources or operations that don't fit any other verb.

Cross-Q: A junior wrote PUT /users or 42 that accepts {email: "new"} and only updates that field. What's wrong?-- think --

A: That's PATCH semantics smuggled into a PUT verb.
The PUT contract says "this is the new resource; replace what's there." If a client sends PUT /users or 42 {email:
"new"} expecting full-replace, every other field becomes null, or the server silently preserves them and now PUT is non-idempotent in a subtle way (different requests produce different states depending on what was there before).
Either honor PUT's replace contract or rename it to PATCH.

Cross-Q²: When would POST ever be correct for an update?-- think --

A: When the operation isn't a resource update but a business action with side effects, POST /orders or 42 or cancel, POST /users or 42 or disable, POST /invoices or 42 or send-reminder. These trigger workflows (refunds, emails, ledger entries) that don't fit "field-level update" semantics.
The sub-action POST pattern is the pragmatic escape hatch, rest purists hate it, but production A P Is use it everywhere because PATCH lies about what's happening.

-- pause --
Drill 2, Idempotency.

Q: List the idempotent H T T P methods and define idempotent.-- think --

A: GET, HEAD, OPTIONS, PUT, DELETE are idempotent. PATCH depends on body semantics. POST is not. Idempotent = N identical requests produce the same server state as one, no extra side effects from retries.

Cross-Q: DELETE is idempotent, but the first call returns 204 and the second returns 404. Doesn't that contradict idempotency?-- think --

A: No, idempotency is about server state, not response equivalence. After the first DELETE, the resource is gone; after the second, it's still gone. State is identical.
The 404 on the second call is informational ("there's nothing here"); some A P Is return 204 on subsequent calls to be friendlier to retries, both are RFC-compliant.

Cross-Q²: PATCH with Jason Merge Patch (RFC 7396), idempotent or not?-- think --

A: Idempotent. PATCH {status: "shipped"} applied twice yields the same state. Jason Patch (RFC 6902) is the non-idempotent variant: [{op: "add", path: "/items/-", value: x}] appends x twice when retried. The verb alone doesn't tell you, the body format does.
This is why "is PATCH idempotent?" is a gotcha, the correct answer is "it depends on the patch document format."

-- pause --
Drill 3, Status code choice.

Q: POST creates a resource successfully. 200 or 201?-- think --

A: 201 Created, with a Location header pointing at the new resource URL. 200 is for successful operations that don't create a resource (read, update). Returning 200 on create breaks every "subscribe to creation events" integration that filters by status code.

Cross-Q: Duplicate-key insert, 409 or 422?-- think --

A: 409 Conflict is the textbook answer, the request conflicts with the current state of the resource.
422 Unprocessable Content (RFC 9110's name for what RFC 4918 called "Unprocessable Entity") is for semantically-invalid bodies that don't conflict with state (for example, "you can't add a 51st item to a 50-item cart").
The distinction: 409 = "your input is fine but the world changed"; 422 = "your input was always going to be rejected by business rules."

Cross-Q²: 400 versus 422, when does each apply?-- think --

A: 400 is for syntactic failures, malformed Jason, missing required field, wrong content-type. The request couldn't be parsed at all. 422 is for semantic failures, Jason parsed, schema validated, but business rules reject it (negative price, invalid date range, item out of stock).
The pragmatic test: if a Postman user fixes their request body without changing the meaning of what they're doing, the original was 400; if they have to change what they want to do, it was 422.

-- pause --
Drill 4, HATEOAS.

Q: What does Richardson Level 3 promise?-- think --

A: HATEOAS, Hypermedia as the Engine of Application State. Responses include links to next legal actions, so clients navigate the A P I by following links rather than constructing URIs from documentation. Theoretically, the A P I can evolve URIs without breaking clients.

Cross-Q: Do production A P Is actually do this?-- think --

A: Almost never. The cost is real (payload bloat, server-side LinkGenerator plumbing) and the benefit theoretical, every consumer is still a human-written client that hard-coded URLs from your OpenAPI spec.
The handful of true Level 3 A P Is are public hypermedia products with truly evolving URIs (PayPal's rest A P I returns links arrays with rel / href / method; HAL or Jason:A P I ship as standards). For internal or B F F-shaped A P Is, Level 2 (verbs + status codes) is the pragmatic ceiling.

Cross-Q²: If your client doesn't follow links, why does HATEOAS exist as a concept?-- think --

A: Roy Fielding's PhD thesis defined rest as a hypermedia architecture, without HATEOAS, you have "H T T P with resource URIs," not rest. The discipline exists to keep the door open to generic clients (browsers, search engines, future agents) that could discover capability dynamically.
It's the same gap as "JavaScript is a Lisp", true at the design level, irrelevant to most working code. Fielding himself has written angry blog posts that "rest A P I" is misused for what is really Level 2 H T T P.

-- pause --
Drill 5, Content negotiation.

Q: Three ways a client can request Jason versus X M L.-- think --

A: (1) Accept: application or json header, the RFC-correct way; the server picks the best format from its supported list. (2) URL extension, /orders or 42.json versus /orders or 42.xml, convenient but breaks rest (the resource is the same regardless of format).
(3) Query parameter, /orders or 42?format set to json, works but pollutes the URI; caches see different keys for the same resource.

Cross-Q: Which is "correct" rest and why?-- think --

A: Accept header. The resource identifier ( /orders or 42 ) should be stable, it identifies what, not how it's serialized. Format is a representation concern, expressed via headers ( Accept from client, Content-Type from server).
Extensions and query params conflate identification with representation.
GitHub does this properly, its media types are all selected via Accept.

Cross-Q²: How do caches handle the Accept header to avoid serving Jason to an X M L client?-- think --

A: Via the Vary: Accept response header. The cache uses (URL, varied headers) as the cache key, so a Jason response and X M L response for the same URL get different keys. Without Vary: Accept, a cache would serve whichever it stored first to all clients regardless of their Accept.
A S P dot NET Core's content negotiation does not auto-emit Vary: Accept, you have to set it explicitly when responses differ by format.

-- pause --
Drill 6, ETags.

Q: Strong versus weak ETag, when each?-- think --

A: Strong ( "abc" ) means byte-identical, every bit of the response body matches. Weak ( W/"abc" ) means semantically equivalent, same content, but bytes may differ (whitespace, Jason property ordering, gzip versus raw).
Use strong for static or precisely-versioned resources; weak for dynamic Jason where you care about equality-by-meaning not equality-by-bytes.

Cross-Q: Walk me through a conditional GET with ETag.-- think --

A: First request: client sends GET /orders or 42; server returns 200 OK with ETag: "v17" and the body. Client caches both. Second request: client sends GET /orders or 42 with If-None-Match: "v17".
Server compares: if current ETag still matches, returns 304 Not Modified with empty body (bandwidth saved); if changed, returns 200 OK with new ETag and new body.

Cross-Q²: Same client, conditional write, what does the flow look like?-- think --

A: Client reads GET /orders or 42 getting ETag: "v17" and the body. User edits. Client sends PUT /orders or 42 with If-Match: "v17" and the updated body.
Server checks current ETag: if still "v17", processes the update and returns 200 OK with new ETag; if changed (someone else updated in between), returns 412 Precondition Failed. Client must re-fetch and merge.
This is H T T P-level optimistic concurrency, mapping cleanly to E F Core's [ConcurrencyCheck] / RowVersion at the data layer.

-- pause --
Drill 7, cores preflight.

Q: When does a browser send a cores preflight, and why?-- think --

A: For "non-simple" cross-origin requests, anything beyond a GET or POST or HEAD with simple headers and application or x-www-form-urlencoded / multipart or form-data / text or plain content type.
The browser sends an OPTIONS request with Access-Control-Request-Method and Access-Control-Request-Headers, and the server must respond with allowed methods or headers or origin before the browser sends the real request. It's the browser asking permission upfront.

Cross-Q: Which requests bypass the preflight entirely?-- think --

A: "Simple" requests: GET, POST, or HEAD with no custom headers (only Accept, Accept-Language, Content-Language, Content-Type is allowed and only with application or x-www-form-urlencoded, multipart or form-data, or text or plain ).
A POST with Content-Type: application or json is not simple, it preflights.
This is why Jason A P Is always preflight even for what looks like a plain POST.

Cross-Q²: How do you reduce preflight overhead in production?-- think --

A: Set Access-Control-Max-Age on the preflight response (for example, 86400 ), browsers cache the preflight result for that many seconds, so subsequent requests skip the OPTIONS round-trip. Chrome caps it at 7200 seconds (2 hours); Firefox at 86400 (24 hours).
Combined with a C D N that handles OPTIONS at the edge, preflight cost drops to near-zero for repeat clients.
The anti-pattern to avoid: caching a cores response without Vary: Origin, a shared cache stores the copy carrying Access-Control-Allow-Origin for one origin and replays it to a different origin, whose browser then blocks it. Vary: Origin is the fix, not the mistake.

-- pause --
Drill 8, rest versus R P C.

Q: Is G R P C rest?-- think --

A: No. G R P C is R P C over H T T P or 2 with Protobuf, it tunnels strongly-typed method calls ( UserService.GetUser(id) ) through H T T P, ignoring rest's resource or verb or status-code discipline. Every G R P C call is a POST to a method-named URL with a binary body.
The H T T P layer is transport; the semantics are R P C.

Cross-Q: G R P C uses URLs and H T T P. What makes it not rest?-- think --

A: rest is about uniform interface constraints, resource URIs, semantic verbs, hypermedia, statelessness, cacheability, layered system.
G R P C violates most of them: URLs are method names not resources, every call is POST regardless of intent, status codes are G R P C-specific (0, 1, 2,.) not H T T P semantics, no cache discipline (everything is uncached POST), no hypermedia.
It uses H T T P as a pipe, not as the architectural style.

Cross-Q²: When do you pick G R P C over rest?-- think --

A: Internal service-to-service, high-volume, latency-sensitive, both sides controlled by you. Protobuf payloads are smaller than Jason, and the gap narrows again once both are gzip- or brotli-compressed, which every production Jason A P I does.
H T T P or 2 multiplexing removes application-layer head-of-line blocking across streams (a lost TCP segment still stalls every stream on the connection, that limit is TCP's, not H T T P or 2's).
Generated client stubs (G R P C-Go, G R P C-Java, G R P C-dot NET) make calls feel like local method invocations.
Pick rest when: public A P Is, browser clients (G R P C-Web exists but is awkward), heavy intermediary caching needed, schema flexibility matters. Modern stacks: rest at the edge (browser-facing), G R P C internally.

-- pause --
Drill 9, RESTful URL design.

Q: /orders or /order ?-- think --

A: /orders, plural. The URL identifies a collection; the collection contains zero, one, or many orders. GET /orders returns a list; GET /orders or 42 returns one.
/order or 42 would imply a singular noun, which is grammatically weird and inconsistent ("the orders endpoint", never "the order endpoint").

Cross-Q: What about verbs in URLs, /get Orders or /orders ?-- think --

A: Always nouns. The verb is the H T T P method (GET, POST, PUT, DELETE). /get Orders, /create Order, /cancelOrderById are R P C-style, they tunnel intent through the path. RESTful: GET /orders, POST /orders, DELETE /orders or 42.
The exception: state-transition sub-actions ( POST /orders or 42 or cancel ) where the action is the operation, not a field update.

Cross-Q²: A team has /customer-addresses and /customer Addresses mixed in their A P I. What's the convention?-- think --

A: Lowercase with hyphens ( /customer-addresses ). Underscores are syntactically legal but visually similar to spaces; camel Case fights URL case-insensitivity rules (H T T P says hostnames are case-insensitive, paths are case-sensitive but conventions vary).
Hyphens are the dominant convention in modern A P I design, GitHub uses kebab-case for most paths ( /check-runs, /code-scanning ). The actual rule: pick one and enforce via linting; inconsistency is worse than any specific choice.

-- pause --
Drill 10, Long-running operations.

Q: A "process video" operation takes 10 minutes. How do you model it in rest?-- think --

A: 202 Accepted pattern. Client sends POST /videos {url:.}; server returns 202 Accepted with a header pointing at a status resource.
Location: /jobs or abc is the common convention; Microsoft's rest A P I guidelines and Azure services use Operation-Location instead (ARM uses Azure-AsyncOperation ) so the header isn't confused with 201's "here is the resource you created".
Client polls GET /jobs or abc periodically; the status resource returns {status: "processing"} to {status: "completed", result:.}. The server never blocks the H T T P connection for 10 minutes.

Cross-Q: Polling is wasteful. What are the alternatives?-- think --

A: (1) WebSocket, bidirectional persistent connection; server pushes "job complete" when done. Right when you have many concurrent jobs and need real-time.
(2) Server-Sent Events (S S E), one-way server to client push over H T T P; simpler than WebSocket for "I just need to know when it's done." (3) Webhook callback, client provides a callback URL in the original request; server POSTs to it when done. Best for server-to-server integrations.
(4) Hybrid: long-poll the status endpoint with Prefer: respond-async, wait set to 60 (RFC 7240), server holds the request open up to 60 seconds and returns immediately when state changes.

Cross-Q²: For a public rest A P I, which would you actually ship?-- think --

A: 202 + polling, because every H T T P client supports it without special handling. WebSocket or S S E require persistent connections that complicate load balancers, retries, and stateless scaling.
Webhooks require the client to expose an inbound endpoint (impossible from a browser or mobile app behind NAT). Polling is "boring but works", Stripe, A W S S three, every major cloud A P I uses 202 + polling for long jobs.

-- pause --
Drill 11, Bulk operations.

Q: How do you model "create 100 orders in one request" in rest?-- think --

A: There's no clean canonical answer, rest is resource-oriented and bulk is procedural. Common patterns: (1) POST /orders accepting an array body, pragmatic, breaks single-resource convention. (2) POST /batches {operations: [.]}, explicit batch resource, returns a batch status.
(3) POST /orders per item with H T T P or 2 multiplexing, rest-pure but expensive. (4) graph Q L or R P C, admit you're outside rest's sweet spot.

Cross-Q: A junior wrote POST /orders accepting both {single object} and [array of objects]. What's wrong?-- think --

A: Inconsistent response shape (single object versus array of results) confuses clients. Mixed status semantics: what's the status code if 90 succeed and 10 fail? 200 lies; 207 Multi-Status exists (from WebDAV) but is obscure; 400 lies.
The senior pattern: separate endpoint POST /orders or batch that always returns a structured per-item result with overall status 200 OK (the batch succeeded; individual items may have errored).

Cross-Q²: Stripe doesn't support batch, why?-- think --

A: Their stance: idempotency keys + parallel POSTs are simpler, and clients should care about per-request status anyway.
A 100-order batch with 3 failures forces the client to write reconciliation logic, easier to just send 100 parallel POSTs with idempotency keys and process responses independently. The trade-off: 100 round-trips versus 1, but H T T P or 2 multiplexing closes that gap.
Bulk endpoints are tempting but typically end up reinventing transactions poorly; rest nudges you toward "one resource per request" for a reason.

-- pause --
Drill 12, Caching.

Q: What does Cache-Control: public, max-age set to 60, s-maxage set to 3600 mean?-- think --

A: public = any cache (browser, C D N, proxy) may store. max-age set to 60 = fresh for 60 seconds in the browser. s-maxage set to 3600 = fresh for 1 hour in shared caches (C D N), overrides max-age for shared caches only. So: browsers re-validate every minute; C D N serves cached for an hour.
The standard pattern for content A P Is.

Cross-Q: Why do I need Vary: Authorization ?-- think --

A: Without it, a cache uses just the URL as key, two users with different bearer tokens hitting /me get whichever response the cache stored first (likely the other user's data).
Vary: Authorization makes the cache include the Authorization header in the key, so each user gets their own cached response. Critical for any per-user endpoint that's marked public or sits behind a shared C D N.

Cross-Q²: What's stale-while-revalidate set to 86400 for, and what's the failure mode?-- think --

A: After max-age expires, the cache may serve the stale copy immediately while refreshing in the background, up to 86400 seconds (24 hours) past expiry. Huge tail-latency win: users see instant responses; only the background fetch waits on origin.
Failure mode: if your data is fast-changing (stock prices, inventory), users see day-old data with no visual indicator. Pair with short max-age (60 seconds) and only on truly cacheable content. Don't apply to user profiles, balances, or anything where staleness has real cost.

-- pause --
Drill 13, Pagination.

Q: Link header versus body envelope for next-page metadata?-- think --

A: Link header (GitHub style): Link:; rel="next". The body is just the array of items; pagination metadata lives in headers. Body envelope (Stripe style): {data: [.], has_more: true, next_cursor: "xyz"}. Items wrapped in an envelope object.

Cross-Q: Which does your team pick and why?-- think --

A: Most modern A P Is lean envelope. Header-based is RFC-correct (RFC 8288, which obsoleted RFC 5988) and keeps the body purely "the resource collection," but headers are awkward to log, hard to parse in some clients, and easy to lose through proxies or CDNs that strip non-standard headers.
Envelope is verbose but discoverable in any H T T P debugger and survives every layer. GitHub uses headers; Stripe and most fintech A P Is use envelopes.

Cross-Q²: A junior puts total_count: 12_847_392 in the envelope of every paginated endpoint. What's wrong?-- think --

A: Computing total_count requires a COUNT(*) query that scans (or estimates) the full filtered set, for cursor pagination on changing data, this is expensive and immediately stale. Stripe explicitly excludes total counts for this reason.
Pattern: provide has_more: true or false (cheap, just check if there's a next page) and never total_count on hot paths. If business needs counts, separate endpoint ( GET /orders or count ) with aggressive caching and explicit "approximate" labeling.

-- pause --
Drill 14, Allow header.

Q: A client gets 405 Method Not Allowed from POST /orders or 42. What header does the response have, and why?-- think --

A: Allow: GET, PUT, DELETE (or whatever the resource supports). The Allow header tells the client which methods this resource accepts, enabling the client to recover ("oh, I should have used PUT").
Without Allow, 405 is a dead end; with it, the client (or its developer) immediately knows the alternative.

Cross-Q: What if the resource supports different methods for different users (for example, DELETE only for admins)?-- think --

A: Tricky, Allow is per-resource, not per-user. RFC 9110 (which obsoleted RFC 7231) says it lists methods the resource supports, not what the current user is authorized for. A non-admin still gets Allow: GET, PUT, DELETE even though their DELETE would 403.
The fix: separate concerns, Allow reflects resource capability; authorization is a separate check that returns 403 if attempted. Don't try to make Allow user-specific; it confuses caching and breaks the spec.

Cross-Q²: How does this relate to OPTIONS responses?-- think --

A: OPTIONS /orders or 42 should return Allow: GET, PUT, DELETE as a discoverability mechanism, same header, used proactively. cores preflight relies on a related header ( Access-Control-Allow-Methods ) that serves the same role for cross-origin requests.
Pattern: implement OPTIONS to return the union of supported methods, and let your 405 handler emit the same Allow header. A S P dot NET Core's routing gives you half of that for free: when the path matches a route but the method doesn't, it returns 405 with an Allow header automatically.
It does not answer OPTIONS with a 200 + Allow, an unmapped OPTIONS lands on the same 405 path unless you map OPTIONS yourself or the cores middleware short-circuits the preflight.

Drill 15, rest versus H T T P A P I.

Q: What makes an A P I "RESTful" versus just an "H T T P A P I"?-- think --

A: An H T T P A P I uses H T T P as transport, any endpoint reachable over H T T P.
A RESTful A P I additionally honors rest's constraints: resource URIs (nouns), semantic verbs (GET or POST or PUT or DELETE matching intent), correct status codes (201, 204, 404, 409, 422.), statelessness (each request self-contained), cacheability, and ideally hypermedia (HATEOAS).
Most "rest A P Is" in production are Richardson Level 2 H T T P A P Is, resource URIs + verbs + status codes, no hypermedia.

Cross-Q: Is POST /api or getOrdersByCustomer {customer Id: 7} rest?-- think --

A: No, verb in path ( getOrdersByCustomer ), wrong H T T P method (POST for a read), no resource modeling. It's an H T T P A P I (it works over H T T P). It's R P C dressed in H T T P clothing.
RESTful version: GET /customers or 7 or orders or GET /orders?customer Id set to 7, noun URLs, correct verb, no business logic in the path.

Cross-Q²: Roy Fielding himself has said "most rest A P Is aren't rest." What's his complaint?-- think --

A: His thesis defined rest as hypermedia-driven, clients discover next actions from response links (HATEOAS), not from out-of-band documentation. Almost no A P I does this. Fielding's view: if your client reads OpenAPI docs to construct URLs, your A P I is "H T T P-with-resources," not rest.
The community has effectively redefined "rest A P I" to mean Richardson Level 2 (which Fielding considers a downgrade), and Fielding has written blog posts venting about the term being co-opted. For interview purposes: know the distinction; in code, ship Level 2 and call it rest like everyone else.

Section 6. Cheat Sheet.

rest = nouns + verbs + status codes + statelessness, not [HttpGet] annotations.
Verbs: GET safe or idempotent, PUT or DELETE idempotent, POST not, PATCH depends on semantics.
Status codes: 201 + Location for create, 204 for empty success, 409 for conflict, 422 for semantic-invalid.
Idempotency-Key header: client UUID + 24 hours server cache makes POST safe to retry.
Richardson Maturity: Level 2 (verbs + codes) is the pragmatic ceiling; Level 3 (HATEOAS) rare.
Content negotiation: client sets Accept, server echoes Content-Type; A S P dot NET Core auto-handles Jason or X M L.
Strong PUT contract: replace whole resource; if calling twice changes state differently, your PUT is broken.
Sub-action POST ( /orders or 42 or cancel ) is the pragmatic out for state transitions with side effects.
Never tunnel errors via 200 OK, breaks every retry middleware, cache, and observability tool.
DTOs decouple wire shape from DB schema; entities-on-wire is how clients break on migrations.

Section 7. Walkthrough, Duplicate orders after a network blip.

Problem: Mobile checkout intermittently creates two orders for the same cart. Customers see "Order placed" once but get charged twice; support tickets spike.

Diagnosis: Open Application Insights / Datadog and filter on OrderCreated events with the same customer Id within 30 seconds, pairs are everywhere.
Capture a failing flow with Charles Proxy or Fiddler on the device: the first POST /orders returns 201 Created but the TCP connection is reset before the body reaches the client (cellular handover). The mobile H T T P client ( URLSession retry policy) replays the POST.
The server has no idempotency layer, so it processes the second body as a new order.

Fix: Add Idempotency-Key support on POST /orders:

Mobile client sends a fresh UUID per logical checkout, replaying it on retry. Store the key + serialized response for 24 hours.

Why it works: The retry now matches an existing key and returns the original 201 response without re-executing payment or inventory side effects. Stripe popularized the pattern for exactly this failure mode.

Section 8. Self-test.

Yes, RFC 7396 merge semantics are idempotent because the second application produces the same target state as the first. RFC 6902 Jason Patch (operation list with add / remove / test ) is generally NOT idempotent, { "op": "add", "path": "/items/-", "value": x } appends twice.
The verb alone doesn't tell you; the patch format does.

(a) H T T P retry middleware (Polly, browser fetch retry, service mesh) won't retry, it sees success. (b) H T T P caches store the error response and replay it to other clients. (c) Observability tools (APM dashboards, alerting) classify it as success and don't fire the error-rate alarm.
The right code is 4xx (client fault) or 5xx (server fault) plus a Problem Details body.

Most clients are written by humans against documentation, not by generic agents that follow links at runtime. The _links payload weight pays no dividend when the iOS team has already hard-coded POST /orders/{id}/cancel from the OpenAPI spec.
HATEOAS only earns its cost on truly evolving public hypermedia A P Is (rare) where clients should be insulated from URI changes.

The sub-action POST is more honest when cancellation triggers side effects (refund, email, inventory release), the URL names the business operation, the verb is correctly non-idempotent if you allow only one cancellation.
PATCH is purer rest but lies about the operation: "I'm just changing a field" hides the workflow. Most A P Is use sub-actions for state transitions and reserve PATCH for true field updates.

422 Unprocessable Content, the request was syntactically valid Jason, the schema validated, but a business rule was violated. 400 Bad Request implies the request itself was malformed (bad Jason, missing required field). 409 Conflict is reserved for state conflicts (concurrent edit, duplicate key).
Returning the right code lets the client pick a recovery strategy: 422 to show user error; 409 to re-fetch and retry; 400 to developer bug to fix.

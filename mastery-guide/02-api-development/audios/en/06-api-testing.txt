Section 1. Why it matters.

The test pyramid for A P Is has more layers than for plain code. Unit tests cover business logic. Integration tests cover the request to response flow through the real middleware, routing and serialization pipeline. Contract tests catch breaking changes between services.
Performance and load tests catch the issues you can only see at scale. Security tests catch what attackers will exploit. Together they're not redundant, each layer catches a different class of bug.

Why interviewers ask: testing depth separates engineers who ship reliable systems from those who ship and pray. Saying "I write unit tests" is junior. Saying "I run unit + integration + contract + load tests in CI, with a smoke-test suite that runs on every deploy" is senior.

The key tension: tests cost time to write and maintain. Pick the right tier for the right concern. Don't unit-test the framework (testing that E F Core executes a query is testing E F Core, not your code). Don't integration-test pure logic (slower than unit tests for the same coverage).

Section 2. Core concepts.

-- pause --
1. Unit testing.

Definition: test a single class or method in isolation, with all dependencies mocked.

Best for: business logic, validation rules, calculations, state machines, edge cases.

The deep-dive (Unit Testing) covers x Unit + Moq fundamentals. this session extends to the A P I-specific tiers.

-- pause --
2. Integration testing.

Definition: test the full H T T P pipeline (middleware, routing, model binding, controller, service, repository) with a real or in-memory dependency stack.

In A S P dot NET Core, WebApplicationFactory spins up the entire app in-process for testing, swapping Kestrel for TestServer, an in-memory IServer. Tests hit the real middleware, routing and serialization pipeline, but there is no socket and no H T T P wire parsing.

For database integration, use Testcontainers to spin up real Postgres or sequel Server in Docker:

This is slower than in-memory but catches issues that in-memory misses (provider-specific sequel, migrations, transactions).
The E F Core team advises against the InMemory provider for testing, a real container or SQLite is the default; InMemory is a fallback for tests that genuinely don't exercise the data layer.

-- pause --
3. Contract testing.

Definition: verify that the contract between services matches expectations on both sides.

Two flavours:

Provider-driven (OpenAPI snapshot): the A P I publishes its OpenAPI spec; consumers validate against the spec. Tests fail if the spec changes incompatibly.

Consumer-driven (Pact): consumers write expectations of how the provider should behave; providers verify against those expectations.

Pact generates a contract file, which the provider's CI runs against. If the provider's response no longer matches, the build fails, before deployment breaks the consumer.

When to invest: cross-team microservices where providers and consumers ship independently.

-- pause --
4. Performance testing.

Definition: measure latency and throughput under specific scenarios.

Tools:
BenchmarkDotNet, micro-benchmarks for code-level perf.
k6, JS-scripted H T T P load generation; great for CI.
NBomber, dot NET-native load testing.
JMeter / Gatling, heavyweight, scenario-rich.

A typical perf test scenario:

Track p50 or p95 or p99 latency, not just averages, averages hide tail latency that real users feel.

-- pause --
5. Load testing.

Definition: find the system's breaking point, at what request rate / concurrency does it fail?

Variants:
Load test: sustained expected peak load (for example, Black Friday traffic for 4 hours). Goal: confirm SLAs hold.
Stress test: push beyond peak until failure. Goal: identify breaking modes (which component fails first?).
Spike test: sudden traffic surge (10 times normal in 30 seconds). Goal: confirm autoscaling and circuit breakers behave.
Soak test: moderate load for 24+ hours. Goal: surface memory leaks, connection-pool exhaustion, slow degradation.

Run load tests in a production-like environment (same instance sizes, same DB). Don't run on the dev laptop and extrapolate.

-- pause --
6. Security testing.

Definition: automated and manual probes for vulnerabilities.

Layers:
SAST (Static Analysis): scan source for known patterns. Tools: SonarQube, Semgrep, GitHub CodeQL.
DAST (Dynamic Analysis): scan running app. Tools: ZAP (formerly OWASP ZAP, it left the OWASP umbrella and is now an independent project, "ZAP by Checkmarx"), Burp Suite.
Dependency scanning: flag CVEs in NuGet packages. Tools: GitHub Dependabot, Snyk, NuGet Audit (runs at restore, on by default in recent SDKs). dotnet list package --vulnerable prints findings but exits 0, it's a report, not a gate.
Penetration testing: manual probing by humans (third-party security firms once a year for compliance-heavy systems).

8. Where the in-memory test server stops.

WebApplicationFactory gives you the app's own Program.cs, its D I container and its middleware pipeline. What it does not give you is a server in the sense production means. TestServer implements IServer by handing the request straight to the pipeline in memory.
Nothing is written to a socket, so an entire category of behaviour is simply absent from the test, and it tends to be the category people assume they have covered.

There is no T L S handshake, so nothing about certificates, cipher selection or client certificates is exercised. There is no protocol negotiation, so how the app behaves over H T T P or 2 or H T T P or 3 is untested.
Kestrel's limits belong to Kestrel: the maximum request body size, the header count and total header size caps, the keep-alive and request-header timeouts are all configured through KestrelServerOptions and none of them can fire when Kestrel was never instantiated.
And because there is no connection underneath the request, anything the app reads off a connection is not what production would supply, the remote IP address a rate-limiting partition is keyed on, the client certificate an authentication handler expects,
the connection lifetime a long-poll depends on.

That is not an argument against the tier; it is an argument for knowing its edge, so you can say in an interview which of your integration tests actually prove something about the wire.
A S P dot NET Core 10 added the opt-out: UseKestrel() on WebApplicationFactory, with overloads taking a port (pass 0 to let the operating system pick a free one) or an Action.
It must be called before the factory is initialised, before any CreateClient() or StartServer() call, and throws InvalidOperationException if you call it afterwards. With it, the client talks over a real loopback socket to real Kestrel, and everything in the paragraph becomes testable.
It also costs a real port, real connection lifetimes and a slower fixture, so it belongs in a small second suite rather than as the default.

In the real world: a document-upload endpoint has an integration test that posts a large file and asserts a 201. It passes, because the in-memory server has no body-size limit to enforce.
The first real upload never reaches the endpoint at all, Kestrel rejects it at its default request-body limit, and the client gets a status code the handler was never given a chance to produce. The team's response is to add logging to the handler, which of course shows nothing.

9. Testing message-driven flows.

Drill 3's Cross-Q² answers a host-lifecycle question: how to stop a BackgroundService interfering with your tests. That is not the same as testing a consumer.
Once part of the system is driven by messages rather than requests, three separate questions appear, and most suites answer none of them:
does the consumer do the right thing with a message, does the system as a whole reach the right state eventually, and does it stay right when the same message arrives twice.

For the first, MassTransit ships a harness. AddMassTransitTestHarness on the service collection registers it, StartTestHarness() on the built provider returns a started ITestHarness, and it runs on the in-memory transport by default.
You then assert against its observer collections, Consumed, Sent and Published, with queries like Any() and SelectAsync(). The important property is that those queries wait for the message to turn up rather than sampling once; how long they are willing to wait is TestInactivityTimeout.
That is what removes Task.Delay from consumer tests, and it is the answer to "how do you assert on something asynchronous without sleeping".

The harness is in-memory, so it does not exercise the broker: no real serialisation over the wire, no prefetch, no dead-letter queue, no redelivery semantics. When those matter, run the actual broker in a container the same way you already run Postgres.
You then lose the in-process observer, so eventual consistency has to be handled explicitly: poll the projection or the A P I you expect to change, on a short interval, against a deadline, and on failure report the last state you observed rather than a bare timeout.
A test that says "expected Invoiced, last saw Pending after 10 seconds" is debuggable; one that says "timed out" is not.

Idempotency is the assertion nobody writes. The usual broker delivery guarantee is at-least-once, which means redelivery is normal operation, not an edge case, a consumer that crashes between writing and acknowledging will see the message again.
The test is blunt: deliver the same message twice, with the same message id, and assert one effect.
The companion assertion is on the outbox: fail the publish after the database write and check that the write did not survive on its own, or that the message is still sitting pending, because "row written, event never published" is the failure mode a transactional outbox exists to prevent.

Contract testing extends here too. Pact is not only for H T T P interactions: a message pact has the consumer declare the shape of the event it can handle, and the provider's build verifies that the event it publishes still satisfies that expectation.
If your H T T P pacts are green and half your integration surface is events, the contract coverage you are describing in an interview is half of what you think it is.

In the real world: an order service publishes OrderPlaced; a billing service consumes it and raises an invoice. The broker is restarted during a cluster upgrade and redelivers a batch of unacknowledged messages.
Billing raises a second invoice for every order in that batch, and finance finds out from customers. Every consumer test in the suite delivered its message exactly once.

10. Composing the test environment with dot NET Aspire.

Drill 11 teaches the hand-rolled version of shared infrastructure: a collection fixture that owns a container, test classes attached to it by attribute, migrations run once at start.
That plumbing is real work and it drifts, because the topology it encodes also exists in the compose file, the deployment manifests and the local dev instructions, and nothing keeps the four in agreement.

dot NET Aspire's testing package inverts this. The AppHost project already declares the graph, which containers exist, which projects depend on which, how connection strings and service discovery are wired, because that is what you run when you press F5.
Aspire.Hosting.Testing lets a test start that same graph: DistributedApplicationTestingBuilder.CreateAsync() gives you a builder, BuildAsync() produces a DistributedApplication, and StartAsync() brings the graph up.
From there app.CreateHttpClient("apiservice") hands you a client already pointed at a named resource, and app.ResourceNotifications.WaitForResourceHealthyAsync("apiservice") gives you a deterministic point to start asserting from instead of a retry loop around the first request.

The trade is honest and worth stating out loud: this starts everything, so it is a heavyweight fixture, one per test collection, never per class, and it still needs a container runtime on the build agent.
It also does not solve state isolation; you still need the reset strategy from the next section. What it removes is the duplicated description of the environment, which is the part that silently goes stale.

In the real world: a service needs Postgres, Redis and a stub for a payment provider. The integration fixture that starts all three, waits for each, and threads connection strings into the factory is owned by whoever wrote it and understood by nobody else.
Six months later the app has gained a second cache, the deployment has it and the fixture does not, and the suite is quietly testing a topology the service no longer runs in.

11. Resetting database state between tests.

Drill 4 and Drill 11 both prescribe resetting between tests, roll back a transaction, or truncate by hand. Both prescriptions have a name-brand implementation and a failure mode that is worth being able to describe.

Respawn is the library.
You create a respawner once per fixture, Respawner.CreateAsync(connection, new RespawnerOptions { DbAdapter = DbAdapter.Postgres, SchemasToInclude =., TablesToIgnore =. }), and it works out the delete order from the foreign-key graph itself,
so nobody maintains a hand-written list of tables that goes stale the moment someone adds one.
Then ResetAsync before each test. The ignore list is where reference data and the migration-history table go, so a reset does not force a re-migration.

Transaction-rollback isolation is the faster, more tempting option, and it breaks in a way that reads as flakiness. Its premise is that everything the test causes happens inside one transaction the test controls.
Through WebApplicationFactory that premise is already false: the request creates its own D I scope and its own DbContext, which is not the instance your test opened a transaction on.
And even in-process, the moment the code under test opens a transaction of its own, explicitly, through an ambient TransactionScope, or because some unit-of-work wrapper commits a step early, the writes inside it are no longer covered by your outer rollback. Rows survive.
The next test in the class fails, on data it never created, in a way that depends on execution order.

Rollback isolation also hides commit-time behaviour by construction. Anything the database only evaluates at commit, deferred constraints, commit-time triggers, is never evaluated, because you never commit. So the one failure the test tier exists to catch is the one it structurally cannot see.

The third option is a template restore, and on Postgres it is both the fastest and the most complete:
build one database with schema and seed data, then create each test's database from it with CREATE DATABASE. TEMPLATE, which, in Postgres's own words, works by copying an existing database, rather than replaying migrations.
sequel Server teams get the equivalent by restoring a prepared backup or reverting a database snapshot. It costs disk and it gives you genuine per-test isolation, which also removes the parallelism constraint Drill 4's Cross-Q² works around.

In the real world: a suite runs green on rollback isolation for a year. Someone adds a service that commits a saga step in its own transaction so a downstream job can pick it up. From that release onwards, roughly one run in five fails somewhere unrelated, depending on which test ran first.
The team spends a week hunting a concurrency bug in application code that does not have one, the rows from the inner commit simply outlived the outer rollback.

12. Minimal A P Is, TypedResults and endpoint filters.

Drill 5's Cross-Q argues against instantiating a controller and asserting on the returned IActionResult: you get none of the framework participation where the interesting bugs live. With minimal A P Is that reasoning partly inverts, and knowing why is a good signal of having actually written them.

If a route handler is a named method rather than a lambda, and it returns a typed union such as Results, NotFound>, then the compiler has already told you the complete set of outcomes.
A test calls the method directly, asserts the result is that union type, casts to the branch it expects, Ok, and reads Value.
Microsoft's own guidance for testing minimal A P Is shows exactly this shape, including the detail that if a handler returns a single typed result such as Ok, no cast is needed at all and Value is available immediately.
Contrast that with Results.Ok(.), which returns an opaque IResult: you cannot inspect the status or the payload without executing it against an HttpContext. The difference is not stylistic.
TypedResults makes the unit test check status code and body shape, which is precisely what the controller test could not do.

What it still does not check is everything between the request and the method: model binding, the filters attached to the endpoint or to its route group, and the metadata that drives the OpenAPI document and authorisation. Endpoint filters are where minimal A P Is concentrate that risk.
A filter implements IEndpointFilter, receives the invocation context and the next delegate, and is attached with AddEndpointFilter on a single endpoint or on a whole group created by MapGroup.
Nothing about a direct handler call runs any of them, and their attachment point, which group, in what order relative to the others, is the thing most likely to be wrong.

So the split is cleaner than it was for controllers. Handler logic and response shape: unit tests, fast, using the typed results. Filter behaviour, binding and group conventions: one integration test per group that proves the filter fires and produces the failure shape you documented.

In the real world: a team moves request validation out of the handlers into an endpoint filter, and attaches it to the inner route group for /orders while the newer /orders/{id}/lines endpoints hang off a sibling group that never got the filter.
Every handler unit test still passes, they never ran a filter in the first place, and the line endpoints accept malformed payloads for a month before anyone notices the missing 400 seconds.

13. Streaming endpoints, G R P C, SignalR, server-sent events.

Everything assumes a Jason request and a Jason response that ends. Three common shapes break that assumption, and a candidate who says "we test our A P I" without noticing is describing a subset of it.

G R P C. Microsoft's guidance names three approaches: unit-test the service class directly, host the app in TestServer from Microsoft.AspNetCore.TestHost and call it with a real generated client, or probe it manually with tooling.
Direct unit testing works because every service method takes a ServerCallContext argument, which the docs' sample supplies through a small helper of its own; if the method reaches for the HttpContext, the sample shows that has to be seeded into the call context's user state or it comes back null.
Streaming methods differ in shape rather than in principle, a server-streaming method is handed an IServerStreamWriter to write into, a client-streaming one an IAsyncStreamReader to read from, so the unit test supplies those and inspects what was written.
The integration route carries more weight here than for Jason, because the serialisation and the status mapping are G R P C's rather than yours.

SignalR. A hub is a class, so a hub method can be unit-tested by constructing the hub and substituting the caller-clients abstraction it sends through.
The catch is the same one Drill 9 raises about Mock: the SendAsync you write in a hub is an extension method, so a substitute configured against it never matches, you have to set expectations on the non-extension method underneath.
For an end-to-end test, a real client connection can be pointed at the in-memory test server by handing the connection an H T T P message handler the test server provides.
That works for the H T T P-based transports; WebSockets over the in-memory server has been a long-standing gap in the framework,
the tracking issue (dotnet or aspnetcore#11888) notes that TestServer integration only works with non-WebSocket transports because all you can replace is the HttpMessageHandler, so tests either force a long-polling transport or run against a real host,
which is one of the better arguments for the real-Kestrel factory from section 8.

Server-sent events. A S P dot NET Core 10 added a first-class result for these: TypedResults.ServerSentEvents, which takes an IAsyncEnumerable> and streams it. SseItem lives in System.Net.ServerSentEvents and carries an event type, an id and the data payload.
The testing trap is mundane and expensive: the response never completes, so an HttpClient call that waits for the whole body will sit there until something times out.
Read the response with HttpCompletionOption.ResponseHeadersRead, consume the stream incrementally, and assert on the first few events under an explicit cancellation deadline.

In the real world: the first test written against a new notifications stream hangs the CI job for its full ten-minute timeout, on every run, because the assertion is await response.Content.ReadAsStringAsync() on an endpoint that by design never closes.
The build is marked flaky and retried; three days later someone reads the endpoint's signature.

Section 3 treats the OpenAPI document as something to diff, commit it, compare the generated one against the committed one, fail the build on an incompatible change. The same document is also a request generator, and that is the higher-yield use of it, because the assertions come for free.

Schemathesis reads an OpenAPI schema (2.0 through 3.2) or a graph Q L one and generates property-based cases from it, then runs each response through a set of named checks. not_a_server_error catches 5xx responses.
status_code_conformance fails a response whose status is not documented for that operation, and content_type_conformance, response_schema_conformance and response_headers_conformance do the same for the content type, the body and the headers against what the schema declares.
There are input-handling checks, negative_data_rejection, positive_data_acceptance, missing_required_header, unsupported_method, a timing check, max_response_time, an auth check, ignored_auth, and stateful ones including use_after_free and ensure_resource_availability.
It runs from a C L I against the schema URL.

The leverage is that you wrote none of those assertions, and the spec is the oracle.
That makes the loop self-reinforcing in a way most teams never set up: a 500 on an undocumented input is a code bug; a well-formed response the schema did not predict is a spec bug; both surface from the same run, and fixing either improves the input to the next one.
It also completes the OpenAPI story the file starts in section 3, the same artefact that gates breaking changes now generates the traffic.

RESTler, from Microsoft Research, attacks the part Schemathesis finds hardest: depth. It infers producer-consumer dependencies between request types from the OpenAPI definition, that B must follow A because B consumes an id that A produces, and learns from the responses it has already seen.
Its own description of the payoff is that this lets it explore deeper service states, reachable only through specific request sequences: the endpoints that need a real resource to exist before they can be reached at all.
Its checkers look for further 500 seconds and for logic bugs such as resource leaks and hierarchy violations.

Both need a disposable environment with synthetic data, for the reason Drill 8's Cross-Q² already gives about active security scans: these tools will send DELETE, and they will mean it.

In the real world: an endpoint documents a 400 for a malformed date. Schemathesis sends an empty string, the parser throws, and the A P I returns a 500 with a stack trace in the body, a bug nobody wrote a test for because nobody thinks to try the empty string.
The status-code check flags it as undocumented before the not-a-server-error check even matters.

15. Chaos testing the resilience policy.

Self-test 4 tests a circuit breaker by pointing it at a fake that returns 500 on demand. That is the right way to prove the policy is configured correctly, and it proves nothing about how the system behaves when a dependency degrades under real load.
Those are different questions and the second one is where outages come from.

Polly v8 has the tooling in the box.
The chaos strategies that used to live in Simmy became part of Polly.Core in version 8.3, with four builder extensions: AddChaosLatency delays a call, AddChaosFault throws, AddChaosOutcome returns a bad result rather than an exception, and AddChaosBehavior runs arbitrary behaviour.
Each takes options deriving from ChaosStrategyOptions, where InjectionRate is the probability that a given call is affected, documented default 0.001, and Enabled is the switch that keeps injection out of environments you did not mean to break.
Note the change from the old monkey policies: a v8 chaos strategy is enabled by default once you add it, so the flag matters.
Place the chaos strategy innermost in the pipeline, or the retry and circuit-breaker strategies wrapped around it never observe the injected failure and you have tested nothing.

The failure worth injecting is latency, not errors. An error is the easy case, the policy sees a fault and does exactly what you configured.
Slowness is what takes services down, because nothing technically fails while the resources healthy requests need are consumed: connections held in the pool, threads parked, requests queued.
Injecting a delay just under your own timeout is the test that reveals whether your timeout is shorter than your caller's, which is the single most common resilience misconfiguration.

The second-order effect only appears at load. A dependency blips, every caller retries, and because they were all triggered by the same event the retries arrive together, a second wave larger than the first, aimed at a service that is already struggling.
Jittered retry delays and a circuit breaker are the mitigations; a chaos run with faults injected across a full load test is where you find out whether they work. A unit test with one caller cannot show you a retry storm, because a storm needs a crowd.

In the real world: a team injects latency into the payments client during a load test and nothing errors, no 500 seconds, no broken circuits, the chaos report looks boring.
What the run shows instead is the request queue growing and unrelated endpoints timing out, because the timeout on the payments call was longer than the gateway's timeout on the whole request.
Every slow payment held a thread and a pooled connection until well after the client had already given up on the response.

16. Workload models and coordinated omission.

Every k6 script in this session uses stages with virtual users. That is a closed workload model, and the distinction between closed and open changes what the resulting numbers mean, which retroactively qualifies most of the percentile talk in sections 4 and 5.

k6's own documentation names the open-model executors explicitly: it implements the open model with two arrival rate executors, constant-arrival-rate and ramping-arrival-rate.
Everything else is VU-driven and therefore closed, constant-vus (the docs' own closed-model example), ramping-vus, shared-iterations, per-vu-iterations, and the runtime-controlled externally-controlled.
In a closed model, as the docs put it, a VU's next iteration starts only when the last one finishes, so the rate at which new requests arrive is coupled to how long the system takes to answer. In an open model, iterations start on a schedule regardless of whether earlier ones have completed.

The consequence is the part people miss. When the system under test slows down, a closed-model test slows down with it: iteration durations rise and the arrival rate of new iterations tapers off.
The generator backs off at precisely the moment a real user population would not, so the latency you record is the latency of a load the system was, by construction, able to keep up with. k6's documentation names this problem: coordinated omission.
Your percentiles are biased low, and the worse the system behaves the stronger the bias, which is exactly backwards from what you want a stress test to do.

Real users are an open model. They arrive because they arrived, not because your last request came back.

So choose by the question. Hold concurrency constant when you genuinely mean "how does this behave with N connected clients", a fixed pool of worker processes, a known number of long-lived sessions.
Use an arrival-rate executor when the question is "can we serve X requests per second", which is what every capacity and peak-traffic test is really asking.
The arrival-rate executors draw VUs from a pool you pre-allocate, and if that pool is exhausted because iterations are piling up, k6 can no longer sustain the target rate, the documentation notes that too low a preAllocatedVUs reduces the duration spent at the desired rate.
When that happens, the shortfall itself is the finding, ahead of any latency figure.

In the real world: a team sizes for a sales peak with a ramp to a fixed number of VUs and reports a comfortable p95. On the day, the checkout queue backs up within minutes.
Nothing about the system was different, the load test had been politely waiting for each response before sending the next request, so it never generated the pile-up that real, indifferent shoppers did.

17. Where the latency threshold comes from.

p(95)<200 and rate<0.01 appear in this session as bare numbers. In an interview, the follow-up is "where did 200 come from?", and "it seemed reasonable" is a bad answer. The chain has names.

The indicator is the thing you measure, the proportion of requests served in under 200 milliseconds. The objective is the target on that indicator over a window: 99% of them, over 30 days.
The error budget is the complement, the 1% you are allowed to miss, and it is what converts an argument about whether a regression is acceptable into arithmetic.
A load-test threshold is just the objective asserted early: the build fails when a change would have spent budget you had not agreed to spend.

The budget also tells you how urgently to react, through burn rate. Google's S R E Workbook defines it as how fast, relative to the objective, the service is consuming its error budget.
For a 99.9% objective, a burn rate of 1 corresponds to a 0.1% error rate and exhausts the budget in 30 days; burn rate 10 is a 1% error rate and exhausts it in three days; burn rate 1,000 is total failure and exhausts it in 43 minutes.
Their recommended starting parameters page on a 14.4 times burn rate sustained over an hour, 2% of a monthly budget in one hour, and again on a 6 times burn rate over six hours, and open a ticket rather than a page at 1 time over three days.
That is the shape worth remembering: multiple windows, so a fast catastrophe and a slow leak both get noticed, at different levels of urgency.

The second half of this is arithmetic that trips up load-test reports specifically: percentiles do not average. Prometheus's own documentation flags avg(http_request_duration_seconds{quantile="0.95"}) as bad and calls the result statistically nonsensical.
The correct move is to aggregate the underlying observations first and compute the quantile afterwards, for classic histograms, histogram_quantile(0.95, sum by (le) (rate(http_request_duration_seconds_bucket[5m]))). The practical rule: you can merge histograms, you cannot merge percentiles.
So a p99 taken per pod and averaged across pods is not the run's p99, and neither is a mean of per-minute p99s over an hour. Keep the buckets, that is what high-dynamic-range histogram structures exist for, and compute the percentile once, at the end, over everything.

In the real world: a dashboard shows p99 latency at 180 milliseconds across a twelve-pod deployment and everyone is happy. The panel is averaging each pod's p99.
One pod is sitting at two seconds because it landed on a noisy node and its connection pool is saturated, a twelfth of all traffic is having a bad time, and the graph that exists to show exactly that is mathematically incapable of it.

Section 6 covers the CVE half of this: scanners, NuGet Audit, a build that fails on a known-vulnerable package. That answers "is anything we depend on known-bad today".
It does not answer the other three questions an incident will ask, is the dependency graph the same one we reviewed, did the packages come from where we think, and what exactly did we ship.

Is the graph the same? Restore resolves transitive versions each time, and the result can move without any change to your project file, a newly published version that matches your range better, a package pulled from the feed, a floating version.
Setting RestorePackagesWithLockFile makes restore write packages lock json at the project root recording the full closure. Once that file exists it is used on every restore even without the property.
In CI you then restore with --locked-mode (or RestoreLockedMode set to true for MSBuild), which, in NuGet's words, will either restore the exact packages listed in the lock file or fail if the declared dependencies changed after the lock file was created.
That turns "the graph moved" from something you discover at runtime into a build failure with a diff attached.

Did they come from where we think?
When a build has more than one feed configured, a private feed for internal packages and nuget.org for everything else, package resolution across both is what dependency confusion exploits:
publish a package publicly under an internal name, at a higher version, and wait for someone's restore to prefer it.
The mitigation is source mapping in nuget.config, which filters per package-ID pattern which source or sources NuGet is allowed to search, map your internal prefix to the internal feed alone and an internal name can only ever resolve internally.
Note that NuGet does let the same pattern be declared on several sources, which reopens the hole; the point of the control is to declare exactly one.
Signature checks are the complementary control: dotnet nuget verify validates a signed package, and NuGet's configuration can be set to require that restored packages carry a signature from an author or repository you trust.

What did we ship? An SBOM is the artefact that answers this after the fact without a rebuild. CycloneDX has an official dot NET generator that produces a bill of materials from a project or solution; Microsoft's sbom-tool produces SPDX-format ones.
Generate it in the release pipeline and attach it to the release, and the question "were we running the affected version on the day the advisory landed" becomes a lookup instead of an archaeology project.

The last piece is secrets. GitHub's push protection blocks a push containing a detected secret and explains why, worth knowing that anyone with write access can bypass it by supplying a reason, and organisations can delegate that bypass, so it is a strong default rather than a wall.
It also only guards what is being pushed now, so pair it with a history scanner such as gitleaks in CI for everything that predates the control.

In the real world: an advisory drops for a logging package on a Friday. The question in the incident channel is not "are we vulnerable", the scanner answers that for main in a minute, it is "which releases in the last six months shipped the affected version".
Without a lock file and a per-release SBOM the only way to answer is to check out old tags and restore them, which resolves a different graph than the one that was built at the time, and the answer you get is not the answer you needed.

-- pause --
19. Coverage you cannot game.

Drill 14 cites 95% line coverage against 65% mutation coverage as a diagnosis, without saying where either number comes from or how it is enforced. Both halves matter, because the enforcement mechanism is what decides whether coverage becomes a quality signal or a number people learn to satisfy.

Instrumentation in dot NET now runs two ways depending on the runner. Under VSTest, coverlet.collector in the test project plus dotnet test --collect:"XPlat Code Coverage" is the long-standing path.
Under Microsoft.Testing.Platform, selectable via global.json with "test": { "runner": "Microsoft.Testing.Platform" } from the dot NET 10 S D K, coverage is an extension:
Microsoft.Testing.Extensions.CodeCoverage adds --coverage, with --coverage-output and --coverage-output-format accepting coverage, xml or cobertura.
Coverlet has an MTP integration of its own, coverlet.MTP, driven by --coverlet and --coverlet-output-format (json, lcov, opencover, cobertura, teamcity).
One migration detail catches people: in the Microsoft extension IncludeTestAssembly defaults to false, where VSTest defaulted to true, so test projects drop out of the report and the percentage moves without anything real having changed.
ReportGenerator then turns whichever format you chose into human-readable reports and merges results across runs.

The practice question is what you gate on.
A single repository-wide percentage floor is the gameable version, and it gets gamed in three predictable ways:
tests that execute code without asserting anything about it, exclusion attributes and filter patterns applied to the awkward files, and new trivially-covered code raising the average while the untested code grows underneath.
Every one of those raises the number and lowers the information.

The non-gameable version gates the diff. Measure coverage of the lines this change touched, not of the repository, and require that to clear the bar; the total is then a trend you watch rather than a threshold you defend.
SonarQube's default quality gate is built on exactly this idea, its conditions apply to new code, with coverage on new code required at 80% or, and the reasoning generalises to any tool:
legacy gaps stop blocking unrelated work, and nobody can raise the number without writing a test for something they actually changed.
Pair that with mutation score on the same changed files, per Drill 14, and you have one metric saying the code ran and another saying the tests would have noticed if it misbehaved.

In the real world: a team adopts an 80% floor. Coverage climbs steadily for two quarters and everyone reports it as a win.
The audit finds three of the four hardest classes in the codebase carry [ExcludeFromCodeCoverage], added in the same pull request that introduced the gate, with a commit message that says "unblock build".

20. Managing flaky tests.

Drill 1's Cross-Q² handles flakiness by shrinking the E2E suite to a smoke suite, the right structural answer, and only half the problem. It reduces how many flaky tests you are exposed to; it says nothing about managing the ones you keep.
At senior level, flakiness is a tracked engineering concern with its own metric and its own workflow, not an annoyance.

Start by defining it measurably: a test is flaky when the same test at the same commit produces different outcomes.
That definition is only usable if you keep results across runs, which means publishing the test-result files your runner already produces and keying them by fully-qualified test name so you can compute a per-test flake rate over time.
Without that history, every conversation about flakiness is anecdote, and the tests everyone re-runs by reflex are known socially rather than institutionally.

Then be careful with retries. A blanket retry-until-green policy converts a genuine race condition into a slow test, and destroys precisely the information you needed, that the code has a timing dependency.
Something intermittently failing under parallel load is usually telling you about a real concurrency bug that will also happen in production, just rarer.
If you retry at all, retry visibly: record that a retry occurred and count it, so that a test that only passes on the second attempt is a tracked defect rather than a green tick.

Quarantine is the workflow that keeps the suite trustworthy while you fix things.
Move the offender out of the blocking run by category, an x Unit trait selected out with a dotnet test --filter expression is enough machinery, keep running it on a non-blocking schedule so you retain the signal, and attach two things without which quarantine becomes a graveyard:
an owner and an expiry date.
At the expiry, the choice is explicit, fix or delete.

The fix-versus-delete criterion is simpler than it sounds: if nobody can state what the test protects, delete it, because a test whose purpose is unknown cannot be maintained. If someone can, the cause is usually one of three, all of which have answers already in this session.
A dependency on wall-clock time, inject TimeProvider and drive it with FakeTimeProvider, per Drill 3. Shared state across parallel classes, the isolation strategies in Drill 4 and section 11.
An assertion racing an asynchronous side effect, poll against a deadline, per section 9, rather than sleeping and hoping.

In the real world: the tell that a team has stopped managing this is behavioural, not numerical. A build goes red, and the first thing anyone does is press re-run, before reading which test failed.
At that point the suite has stopped being a gate; it is a slot machine that eventually pays out, and a real regression will get through it the same way a flake does.

21. Verification after deploy.

The file's post-merge story ends at two artefacts: smoke tests after the stage deploy, and Drill 1's five-to-ten test smoke suite with a rollback on failure.
Both are sound, and both share an assumption worth challenging, that the deploy either works or it does not, and you find out by asking the system a handful of synthetic questions. Progressive delivery replaces that with a graded exposure, and it is where a lot of senior testing practice now lives.

Canary releases put the new version in front of a fraction of real traffic and compare it against the old one while both are running. The tooling automates the comparison: Argo Rollouts and Flagger both shift traffic in steps and run an analysis at each step, promoting or rolling back on the result.
The senior detail is what you compare against.
A canary judged against a fixed threshold tells you very little, because the threshold has to be loose enough to survive a normal Monday; judged against the baseline version taking the same traffic at the same moment, a regression shows up as a difference even when both are within the threshold.

Shadow or mirrored traffic takes it a step earlier: send a copy of live requests to the new version and discard its responses. You learn whether it can parse and handle the real distribution of inputs, which is invariably stranger than your test fixtures, with no user-visible risk.
The trap is side effects. A shadowed service that writes to the same database, calls the same payment provider or publishes to the same topic is not shadowing, it is double-processing.

Feature flags separate deploy from release, so the unit of rollback becomes a flag flip rather than a redeploy, measured in seconds and requiring no pipeline.
The cost is that every live flag is a branch in production behaviour that your tests would have to cover in combination, so flags need removal dates as firmly as quarantined tests do.

Synthetic monitoring is the smoke suite that never stops, the same critical journey, run on a schedule from outside your network, so a broken checkout is found by your own probe rather than by a customer.
And the alert that ties this section back to section 17 is the burn-rate alert:
you do not page on a canary's raw error count, you page on how fast that error rate is consuming the error budget, which is the only framing that keeps a small absolute number in a low-traffic window from either screaming or hiding.

In the real world: a canary runs for twenty minutes at a small traffic share, well inside its error-rate threshold, and is promoted automatically.
Its p99 was materially worse than the baseline pod's the whole time, but the analysis compared against a fixed number rather than against the version running beside it, so nothing objected.
The regression reaches full traffic at the start of the business day, when the extra latency finally pushes the shared connection pool over.

Section 4. Common pitfalls.

Unit-testing the framework. A test that asserts "E F Core executed a query" tests E F Core, not your logic. Test what you wrote.
Integration tests with shared state. Tests that depend on order of execution. Each test should be independent, WithWebHostBuilder gives you a fresh server per test class.
No assertion on response shape. Asserting 200 OK only, but the body could be empty or malformed. Deserialize and check.
Mocking what you own. If you wrote IUserRepository, write integration tests against the real DB, not unit tests with a mock that just confirms your mock returns what you told it to.
Slow unit tests. If a unit test takes > 100 milliseconds, it's probably an integration test in disguise, using a real DB or real H T T P. Move it to the integration tier.
Brittle tests on U I / E2E layer. They break when CSS changes. Keep E2E to a smoke suite covering critical paths only.
Performance test from the dev laptop. Local network, local C P U. Run from a peer environment with realistic latency.
Reporting only average latency. Hides tail problems. Report p50 or p95 or p99 or max.
No load test before launch. "It worked in dev." Production has 1000 times the load. Surprises are guaranteed.
Stub returns happy path only. Real services error. Test with stubs that return 5xx, timeout, slow responses.
Hardcoded test data that drifts from production shape. Use builders / factories to keep test data in sync with DTOs.
No test for security regressions. When auth changes, run the security test suite. SAST + DAST in CI.

Section 5. Interview-ready summary.

Test pyramid: many unit, fewer integration, fewer still contract, very few E2E.
Unit: isolated business logic with mocks. Fast, deterministic.
Integration: the real pipeline in-process via WebApplicationFactory ( TestServer, no socket). Real DB via Testcontainers.
Contract: Pact for cross-service expectations.
Perf / load: k6, NBomber, BenchmarkDotNet. Track p95 or p99 not just average.
Security: SAST + DAST + dependency scanning in CI.
Mocks versus stubs versus fakes: mock for verification, stub for canned data, fake for working in-memory implementation.

Expected interview questions:

"What's the difference between unit and integration tests?", Unit isolates one class with mocks (fast, fragile-to-implementation). Integration covers wiring with real dependencies (slower, fragile-to-config).
"How do you test an A S P dot NET Core A P I endpoint?", WebApplicationFactory, override D I via ConfigureTestServices (point EF at a test container), HttpClient against the in-memory TestServer, assert status + body.
"What's a contract test and why does it matter?", Verifies that one service's expectation of another matches reality. Pact lets consumers express expectations; providers verify in CI. Catches breaking changes before deployment.
"How do you measure A P I performance?", k6 / NBomber generates H T T P load, capture latency percentiles (p50 or p95 or p99), throughput (requests per second), error rate. Run in production-like environment.
"Average latency versus percentiles?", Average hides tail behavior. p99 tells you what 1% of users experience. Optimize for p99 first if customer-facing.
"Mock versus stub?", Stub returns canned data ("here's a fake user"). Mock verifies interactions ("was Save called once?"). Use stubs to set up scenarios; mocks to assert behavior.
"How do you test that your auth layer rejects unauthorized access?", Integration test that calls protected endpoint without Authorization header, asserts 401. Plus tests for valid token, expired token, wrong role.

Section 6. Interview Cross-Questioning Drill.

️ Honest caveat: reading this once doesn't make you interview-ready. Cover the answers, write them cold, then check. Pair with a senior for live mock cross-questioning. The guide removes "I never thought about that" surprises; mock interviews convert knowledge into reflex. Both are needed.

Each drill is Q to A to Cross-Q to A to Cross-Q² to A.

-- pause --
Drill 1, A P I test pyramid proportions.

-- think --Q: What's the rough proportion of unit, integration, and E2E tests for an A P I service?

A: For a typical service, roughly 70% unit, 25% integration, 5% E2E by test count. Unit tests are fast and many, every branch in business logic. Integration tests cover wiring (H T T P route to middleware to controller to service to DB), typically one happy path + 2-3 error paths per endpoint.
E2E (full-stack smoke tests against staging) cover only critical user journeys, checkout flow, login flow.

-- think --Cross-Q: A team has 10,000 unit tests and 50 integration tests. CI runs in 8 minutes. They have constant production bugs in H T T P wiring. What's the diagnosis?

A: Coverage shape is wrong. The unit tests are exercising business logic deeply but never validating the wiring layer (request binding, middleware order, serialization edge cases, route conflicts). Many "passing unit tests, failing prod" stories come from this gap.
Diagnosis: shift the ratio, fewer unit tests for trivial code, more integration tests covering each endpoint's actual H T T P contract. Aim for at least one integration test per endpoint that validates status code, response shape, and authentication behavior.

-- think --Cross-Q²: E2E tests are flaky and slow. The team disables them. What's the compromise?

A: Replace large E2E suites with a tiny smoke suite (5-10 tests) that runs against staging post-deploy: login, create one resource, read it, delete it, logout. If the smoke suite breaks, deployment is rolled back.
Flakiness comes from full E2E suites with hundreds of tests covering many U I paths; trimming to "is the system alive end-to-end?" gives you the safety net without the maintenance overhead. Pair with contract tests for cross-service coverage, those are deterministic where E2E is fragile.

-- pause --
Drill 2, Contract testing (Pact).

-- think --Q: What does Pact solve that integration tests don't?

A: Cross-team breaking-change detection without coordinated deploys. Integration tests verify your service against your dependencies.
Pact verifies that consumer team A and provider team B agree on the contract, consumer writes expectations ("I'll send GET /orders or 42; I expect status 200 with {id, total} "), provider's CI replays those expectations against the real provider and fails if the response no longer matches.
The provider learns about a breaking change before deploy, not after the consumer's request errors flood.

-- think --Cross-Q: When is Pact overhead rather than win?

A: When (a) one team owns both consumer and provider, internal integration tests already cover the same ground; (b) the A P I is consumed by a single hand-rolled client where regression risk is low;
(c) the team isn't disciplined about running provider verification in CI, Pact files drift from reality and give false confidence.
The win requires the ownership boundary, separate teams, separate release cycles. Without that, the ceremony costs more than the safety.

-- think --Cross-Q²: Pact-broker, Pact-flow, and OpenAPI-based contract tests, when do you use each?

A: Pact-broker (free, self-hosted), coordinate contracts across teams in a single org, modest scale. Pact-flow (paid, hosted), same but with secrets management, audit trails, integrations with deployment pipelines for "can I deploy?" gates.
OpenAPI-snapshot-diff (for example, oasdiff ), when you own both sides or the provider doesn't want to run consumer-driven contracts;
cheaper, but it only catches breaking shape changes, not "this header was always required and the spec didn't say so" gaps that Pact catches by actually replaying requests.

-- pause --
Drill 3, WebApplicationFactory.

-- think --Q: What does WebApplicationFactory bootstrap?

A: It hosts your entire A S P dot NET Core app in-process, same Program.cs, same D I container, same middleware pipeline, same routing, but it replaces Kestrel with TestServer, an in-memory IServer.
The HttpClient it hands you writes straight into that server, so there is no port, no socket and no H T T P wire parsing.
Tests exercise the request pipeline (model binding, validation, controller dispatch, response serialization) but not the parts Kestrel owns, T L S, H T T P or 2 and H T T P or 3, request-size and header limits, real client IPs.

-- think --Cross-Q: ConfigureServices in WithWebHostBuilder runs after Program.cs 's registrations. How do you override a registration like the real DB connection?

A: services.RemoveAll>();, plus, on E F Core 9+, IDbContextOptionsConfiguration and the AppDbContext registration itself, since removing the options alone leaves the original configuration in place, then services.AddDbContext(.) with the test config.
The order matters: Program.cs registers the production database; your test override removes that registration and re-adds the test one.
Put the override in ConfigureTestServices ( Microsoft.AspNetCore.TestHost ) rather than plain ConfigureServices, it's the hook meant for test overrides, so using it states that intent at the call site.
Some teams encapsulate this in a custom WebApplicationFactory subclass per test scenario to avoid repeating the override in every test.

-- think --Cross-Q²: Async background services (for example, a BackgroundService that polls a queue) start running when the host starts. How do you handle them in tests?

A: Three options. (1) Skip them, replace the registration in the test config: services.RemoveAll();. Useful when the test isn't about the background work. (2) Run them deterministically, replace the real queue with a fake that the test controls; trigger work and assert outcomes synchronously.
(3) Embrace the asynchrony, let them run but drive the clock: have the service take TimeProvider (BCL, dot NET 8+) and register FakeTimeProvider ( Microsoft.Extensions.TimeProvider.Testing ) in the test, then advance time to fire its delays.
(Rx's TestScheduler was the pre- TimeProvider workaround.) Option 1 is most common; option 3 is necessary when the test is about the background work.

-- pause --
Drill 4, Test isolation and shared state.

-- think --Q: A test passes alone and fails when the full suite runs. Diagnose.

A: Shared state leak. Suspects: static fields, singleton services (especially DbContext), file-system fixtures not cleaned up, environment variables modified by one test that survive into another, database state from one test visible to another (no transaction wrap), test ordering assumptions.

-- think --Cross-Q: A team uses IClassFixture> for integration tests. Two tests in the same class hit /orders, first creates an order, second asserts the list is empty. Second test fails. Why?

A: IClassFixture shares the factory (and the test database it is wired to) across all tests in the class. Test 1's seeded order is still in the DB when Test 2 runs.
Two fixes: (a) reset state between tests, IAsyncLifetime.InitializeAsync clears the DB before each test; (b) wrap each test in a transaction that rolls back, using var scope = factory.Services.CreateScope(); var tx = scope.ServiceProvider.GetService().Database.BeginTransaction();
test runs inside, rollback on dispose.
(c) Switch to IClassFixture per-class but seed in InitializeAsync so state is deterministic.

-- think --Cross-Q²: Parallel test execution, x Unit runs test classes in parallel by default. What pitfalls?

A: (1) Shared external resources, same DB, same file path, same port. (2) Static fields touched concurrently. (3) Singleton services in the WebApplicationFactory (cache, in-memory store) collide if two test classes use the same factory instance.
Mitigation: use [Collection] attribute to serialize tests sharing a resource, or use unique-per-test resources (random DB name, random file path). Testcontainers spins up a fresh container per test class by default, pricey but bulletproof.

-- pause --
Drill 5, Integration versus unit boundary.

-- think --Q: Where do you draw the line, what's a unit test versus an integration test in the A P I world?

A: Unit test: one class, dependencies mocked or faked, no external I O (no H T T P, no DB, no file system). Integration test: the real wiring is exercised, H T T P request enters the framework, traverses middleware, hits the controller, calls the service, persists to a test-container DB.
The threshold is "is there any I O or framework participation?"

-- think --Cross-Q: A test instantiates Controller, calls a method directly, and asserts the returned IActionResult. Is this unit or integration?

A: Unit, and arguably a low-value one. You're testing the controller's logic without the framework's model binding, validation, content negotiation, authorization filter, action filter, or exception handling.
The bugs you usually want to catch in a controller, wrong status code based on request shape, validation errors mapped wrong, response missing a header, all live in framework participation. Direct controller instantiation lets the framework's actual behavior surprise you in prod.
Push these to integration via WebApplicationFactory unless the controller has substantial pure-logic methods.

-- think --Cross-Q²: Where do you put validator tests, unit or integration?

A: Unit. A FluentValidation validator is a pure function: input DTO to set of validation errors. No H T T P, no DB, no framework. Test it directly with validator.TestValidate(dto) and assert specific failures.
Reserve integration tests for "does the controller actually invoke this validator and return 400 with the errors in the right shape?", usually one or two integration tests per controller cover that wiring; the deep validator coverage lives in fast unit tests.

-- pause --
Drill 6, Performance testing tools.

-- think --Q: k6, NBomber, BenchmarkDotNet, when do you reach for each?

A: BenchmarkDotNet, micro-benchmarks for code-level perf: "how long does this method take?", "what's the allocation count?". Used during optimization, runs in-process, sub-microsecond precision.
k6, H T T P load testing, JS-scripted scenarios, great for CI integration, can simulate thousands of VUs from a single host. NBomber, dot NET-native load testing, useful when you want to share C sharp DTOs and validation logic between production code and load scripts.

-- think --Cross-Q: A team writes BenchmarkDotNet tests for an A P I endpoint. What's wrong with that?

A: BenchmarkDotNet measures in-process method performance, it won't accurately capture H T T P serialization overhead, network latency, connection pool dynamics, garbage collection pauses across requests, or thread pool starvation.
For an A P I endpoint, the relevant measurement is throughput and tail latency under realistic concurrency, which means k6 or NBomber against the running service in a production-like environment.
Use BenchmarkDotNet for the hot algorithm inside the service; use H T T P load testing for the endpoint as a whole.

-- think --Cross-Q²: BenchmarkDotNet reports "Mean: 100ns, StdDev: 5ns". Is that useful?

A: Only if you also look at allocation count, garbage collector stats, and tail percentiles. A 100ns mean with 0 allocations is qualitatively different from 100ns mean with 1 allocation per call, the latter cumulatively pressures gen0 garbage collector in a hot loop.
BenchmarkDotNet reports Allocated per invocation and gen0 or gen1 or gen2 collection counts; read those alongside mean time.
For real perf characterization, enable [MemoryDiagnoser]; if you want tail behaviour, add percentile columns yourself via a custom config ( StatisticColumn.P ninety-five ), the default output is mean, error and standard deviation, with no percentiles.

-- pause --
Drill 7, Soak test versus load test.

-- think --Q: What's a soak test, and what does it catch that a load test doesn't?

A: A load test runs at expected peak load for a short duration (10-60 minutes) to confirm SLAs hold.
A soak test runs at moderate load for 24+ hours to surface time-dependent failures: memory leaks, connection-pool exhaustion, file-descriptor leaks, slow garbage collector degradation, log rotation failures, certificate expiry, scheduled-job interference.
The "slow drip" failure modes that need time to accumulate.

-- think --Cross-Q: A service passes a 30-min load test (1000 requests per second, p99 = 80 milliseconds, no errors). Two days into production, pods are OOM-killed every 6 hours. What likely class of bug?

A: Memory leak, accumulating retained references over hours. The 30-min load test ran long enough for memory to climb modestly but not enough to trigger OOM.
Common causes: singleton-scoped DbContext, unbounded in-memory cache, event handlers never unsubscribed, async state machines retaining context. Diagnosis: heap snapshot with dotnet-dump, look at top retainers, trace ownership graph. Fix the offending lifetime or cleanup.
Prevention: nightly soak test (4 hours+) with heap-growth assertion.

-- think --Cross-Q²: How do you assert heap stays bounded in an automated soak test?

A: Three patterns. (1) Sidecar that polls /metrics (Prometheus) every minute for dotnet_total_memory_bytes or process_working_set_bytes; assert at end-of-test that growth from baseline is < threshold (for example, 50%).
(2) Inside the load script (k6 has the BrowserMetrics extension; NBomber lets you embed assertions on custom counters), periodically probe a /diagnostics or memory endpoint and fail if working set exceeds a hard cap.
(3) Post-test: trigger a heap dump, run dotnet-gcdump analysis, fail if any type's instance count grew unboundedly. The pattern that wins depends on infrastructure; the principle is "memory growth on a steady requests per second is a leak; flat is healthy."

-- pause --
Drill 8, Security testing in CI.

-- think --Q: How do you integrate ZAP or Burp into CI?

A: ZAP has a C L I mode and a GitHub Action, point it at your staging deployment URL, run a baseline scan (passive, fast) or a full scan (active, slow). Burp Suite Professional has a C I C D integration via the BurpSuite Enterprise Edition (paid).
The typical flow: deploy to staging, run ZAP baseline as part of post-deploy verification, fail the build on critical findings (high-confidence XSS, SQLi). Save the report as a build artifact for review.

-- think --Cross-Q: A team's ZAP baseline scan finds 50 "informational" findings on every run. They mute them all. What's the trap?

A: The mute list grows until real findings hide in noise.
The fix is tuning: review each informational finding once, most are CSP-related, header-related, or low-impact configuration issues; either fix them at the source (set the missing header, tighten CSP) or add them to ZAP's per-rule ignore list with a code comment explaining why each is suppressed.
Periodically re-audit the ignore list. Distinguish "informational findings we've decided to accept" (documented) from "informational findings we haven't looked at" (a future hidden critical).

-- think --Cross-Q²: Active ZAP scans against staging risk damaging test data. How do you isolate?

A: Three patterns. (1) Dedicated security-test environment with synthetic data, refreshed nightly, no shared use. (2) Limit ZAP's scan scope: configure to skip destructive endpoints (DELETE), throttle requests per minute, set a budget on test duration.
(3) Run active scans against a deployment of the current pull request in an ephemeral environment that's torn down after, no impact on other testers.
The mistake is running active scans against shared staging during the day; everyone's tests start failing because ZAP submitted 10,000 form posts with malicious payloads.

Drill 9, Mocking external services.

-- think --Q: WireMock.Net versus handcrafted fakes, when does each win?

A: WireMock.Net for H T T P dependencies, payment gateway, third-party A P I, an external microservice. It's a real H T T P server (in-process) that responds based on configured request matchers, supports stateful behavior, recording or replay, latency simulation, fault injection.
Handcrafted fakes ( class FakeOrderRepository: IOrderRepository ) for in-process dependencies, repository, message bus, time provider, where you don't need H T T P at all.

-- think --Cross-Q: A team mocks an external H T T P A P I by injecting Mock instead of using WireMock. What goes wrong?

A: HttpClient is hard to mock cleanly, it's not an interface; methods are virtual but the typical extension methods ( GetAsync, PostAsJsonAsync ) call into SendAsync which is awkward to stub.
You miss real behaviors: H T T P-level headers, content negotiation, status code to exception mapping, retry logic in DelegatingHandler.
WireMock at the network layer (loopback in-process) exercises the real HttpClient against a real H T T P endpoint, much closer to production behavior with less brittle test code.

-- think --Cross-Q²: WireMock supports request matching, response stubbing, and stateful behavior. When do you need stateful tests versus stateless?

A: Stateless ("always return this response for any GET /charge") works for most happy-path tests, exercise that your client handles the response correctly.
Stateful is needed when the test asserts a sequence: "POST /order creates an order; subsequent GET /order/{id} must return what we just created with a server-generated ID." WireMock's WithCallback lets you compute responses dynamically from request state.
Don't over-invest, stateful tests are slower and more brittle; reach for them when you genuinely need to verify request-response correlation.

-- pause --
Drill 10, Property-based testing.

-- think --Q: When is property-based testing (FsCheck, FsCheck.Xunit) the right tool?

A: When the system under test has a property that should hold for all inputs of some shape, not just example values.
Classics: "for any string s, Jason.parse(Jason.stringify(s)) == s" (round-trip), "for any list of integers, sort(sort(list)) == sort(list)" (idempotence), "for any valid input to my parser, the result re-serializes to an equivalent input." FsCheck generates random inputs, finds counterexamples,
shrinks them to a minimal failing case.

-- think --Cross-Q: When is property-based testing overkill?

A: When the behavior is fundamentally enumerable or the input domain is tiny, testing a state machine with 5 states by generating random inputs is silly; just enumerate.
When the property is hard to express formally, "does the response look right?" doesn't translate to a property; example-based tests with hand-curated cases are better.
When the function has many side effects that can't easily be undone in a property check, FsCheck assumes generated test cases are cheap to retry, which doesn't hold for tests that hit external services.

-- think --Cross-Q²: A property-based test finds a counterexample after 5000 iterations and shrinks it to a 3-character string that breaks parsing. What do you do?

A: (1) Reproduce: add the shrunk counterexample as a hard-coded example-based test so future runs always check it. (2) Diagnose: trace why the parser fails on that specific input, usually it reveals a missing edge case (Unicode normalization, empty-string handling, whitespace).
(3) Fix and re-run the property test; the iteration count should increase before failure or the test should pass entirely. (4) Add similar test for related shapes, if "áb" (combining character) broke parsing, manually add other combining-character cases.
Property-based tests find one bug each; treat them as guided fuzzing rather than complete coverage.

-- pause --
Drill 11, Testcontainers versus in-memory database.

-- think --Q: Why is UseInMemoryDatabase controversial for integration tests?

A: It ignores sequel provider behavior, no transactions, no concurrency tokens, no foreign-key constraints enforced at the DB level, no migrations, no provider-specific sequel features ( LIKE collation, Jason queries, RAISERROR ).
Tests pass; production explodes on the first concurrent update or on a query that translated fine for sequel Server but Postgres rejects. Testcontainers runs the actual target database in Docker, slower (10-30 seconds setup per test class) but the behavior matches production.

-- think --Cross-Q: A team's CI takes 25 minutes because Testcontainers spins up Postgres per test class. How do you optimize?

A: Three patterns. (1) Share one container across the entire test run via x Unit collection fixtures, IClassFixture doesn't work cross-class; use ICollectionFixture and [Collection("postgres")] on test classes.
(2) Migrations once at startup; reset state per test via transaction rollback or TRUNCATE. (3) Run integration tests in parallel where possible, multiple test classes can hit the same container if they use unique schema or database names.
The combination cuts CI time substantially without losing the real-DB fidelity.

-- think --Cross-Q²: A team uses Testcontainers locally but UseInMemoryDatabase in CI "for speed." When is that defensible?

A: Almost never. The pathology: tests pass in CI (in-memory), fail locally (real DB), or worse, vice-versa. Developers stop trusting either result. The right axis is local-versus-CI consistency, not local-versus-CI optimization.
Either both use Testcontainers and accept the time cost, or both use a shared dev-DB fixture. The single exception: pure controller-shape tests that genuinely don't touch the DB layer can use in-memory and the rest run against the real DB. Two test categories, not two test environments.

Drill 12, Authentication in tests.

-- think --Q: How do you handle authentication in integration tests, bypass or real flow?

A: Both, depending on what's tested. For tests of business logic that requires auth, bypass: register a test authentication handler that always returns a known ClaimsPrincipal with configurable claims.
For tests of the auth flow itself, login, token refresh, role enforcement, exercise the real flow with a test user.

-- think --Cross-Q: Concrete pattern for the bypass handler?

A: Subclass AuthenticationHandler, override HandleAuthenticateAsync to return AuthenticateResult.Success(new AuthenticationTicket(.)) with the claims you want. Register the scheme in the test factory: services.AddAuthentication("Test").AddScheme("Test", _ goes to {}); and set as default.
Tests then set claims via a per-test mechanism, often a header X-Test-User-Id that the handler reads and converts to claims. Real auth middleware is replaced; the rest of the auth pipeline (authorization handlers, policy evaluation) runs unchanged.

-- think --Cross-Q²: A test asserts that an admin endpoint returns 403 for a non-admin user. The bypass handler is set to admin globally. How do you parameterize per-test?

A: Three patterns. (1) Header-driven: X-Test-Role: User versus X-Test-Role: Admin; the handler reads the header per request. (2) Test-scoped service replacement: each test class registers its own IUserPrincipalProvider returning the role for that class.
(3) Factory subclass per scenario: AdminTestFactory and UserTestFactory with different defaults. Header-driven is most flexible for tests that need to switch users mid-test; factory subclass is cleanest for tests that always run as one role.

Drill 13, Snapshot testing for A P I responses.

-- think --Q: When is snapshot testing ( Verify, Snapshooter ) useful for A P I responses?

A: When the response shape is large and stable, and you want regression protection against accidental shape changes. Example: a complex aggregation response with 30 fields.
Hand-coding Assert.Equal for each field is tedious; snapshot test captures the response Jason to a .received file, compares to .verified file, fails on diff. Good for "I never want this output to change without me reviewing it."

-- think --Cross-Q: When does snapshot testing become a maintenance burden?

A: When the response includes volatile fields (timestamps, UUIDs, pagination cursors), every run differs, so every test fails until you scrub the volatile fields with a converter or ignore them.
Also when the snapshot covers too much surface area, one harmless change ripples into 50 failed snapshots. Mitigations: configure snapshot converters to redact timestamps, use multiple smaller snapshots rather than one giant one, snapshot a subset (for example, schema only, not full data).

-- think --Cross-Q²: A snapshot test fails. Junior dev runs the "accept all" command to update snapshots. What's the trap?

A: They've just accepted a regression as the new baseline. The original snapshot existed to catch unintended changes; auto-accepting defeats the purpose.
The discipline: snapshot updates require review (treat .verified file changes like code changes in pull request review), CI fails on any .received file present (forces author to explicitly accept changes locally before pushing).
Tools like Verify support an "approval workflow" where the diff is presented to the developer in a diff tool before acceptance, friction is the feature.

Drill 14, Mutation testing.

-- think --Q: What does Strykerdot NET catch that line coverage doesn't?

A: Whether the tests would fail if the code changed in a subtle way. Stryker introduces "mutations", replace > with >=, swap true with false, change + to -, remove a method call, and runs the test suite.
If tests still pass with the mutation, you have a coverage gap: the line was executed but no test actually asserted the value that the mutation changed. Line coverage says "this line ran"; mutation coverage says "this line ran and the tests would catch a change."

-- think --Cross-Q: Stryker reports 65% mutation coverage on a service with 95% line coverage. What does that signal?

A: 30% of the lines are exercised but not validated. Common causes: tests assert "result.IsSuccess" but not the specific value returned, tests assert one branch but not boundary conditions ( < mutated to <= survives), tests cover the happy path without checking error messages.
Fix: review mutations that "survived", Stryker shows you each one, and add assertions that would catch them. Don't chase 100% (some mutations are equivalent to the original; some are economically not worth catching), but 65% to 85% closes the meaningful gaps.

-- think --Cross-Q²: Stryker is slow, running the full test suite per mutation can take hours. Optimization?

A: Three levers. (1) Scope: run on changed files only in CI (Stryker has incremental mode); full suite weekly. (2) Test selection: link mutations to tests via coverage data; only re-run tests that exercised the mutated line.
(3) Parallelization: Stryker can run mutations in parallel processes; tune to CI host's C P U count. The right setup runs mutation testing on each pull request for changed files (~5-10 min) and full-codebase mutation on nightly cron (multi-hour). Report trend; investigate regressions.

Drill 15, A P I tests in CI duration.

-- think --Q: How long is too long for the A P I test suite in CI?

A: Heuristic: 5 minutes for pull request feedback, 30 minutes for merge-to-main, 4 hours for nightly. Beyond 5 min on pull request, developers context-switch and lose flow. Beyond 30 min on main, batching becomes complex.
Beyond 4 hours overnight, the feedback loop on regressions stretches to "we'll see tomorrow."

-- think --Cross-Q: A team's pull request pipeline takes 45 minutes. How do you trim?

A: Tiered execution. (1) pull request pipeline runs fast tests, unit + lint + build + smoke integration (a couple endpoints), under 5 min. (2) Merge-to-main pipeline runs everything, full integration, contract verification, maybe a tiny load smoke, under 30 min.
(3) Nightly runs soak, full security scan, mutation testing, larger load tests. The pull request is a "is this pull request sane?" gate; merge is "is this branch safe to deploy?"; nightly is "are the slow-burn issues still healthy?" Trying to run all three on every pull request is the failure mode.

-- think --Cross-Q²: A test consistently takes 8 minutes alone. Worth keeping?

A: Investigate the why. If it's a real integration test exercising 50 endpoints sequentially, parallelize. If it's a Testcontainer spinning up Postgres for one assertion, share the container across tests. If it's a await Task.Delay(60) polling loop, replace with deterministic state injection.
If genuinely irreducible (for example, the test verifies a 5-minute cache eviction), move it from pull request to nightly and add a faster mock-based test that verifies the eviction logic without the real timer.
"Slow but valuable" is rare; usually slowness signals an unidentified design problem in the test itself.

Section 8. Walkthrough, Memory leak found by a soak test, not a load test.

Problem: A new orders microservice passes load testing (1000 requests per second for 10 minutes, p99 = 80 milliseconds, no errors). Two days into production, pods are OOM-killed every 6 hours. RAM grows linearly from 200MB to 1.8GB before crash.

Diagnosis: Reproduce locally with dotnet-counters monitor -p, gen2-gc-count is climbing but gen2-gc-collection-count isn't reclaiming much. Switch to dotnet-dump collect to grab a heap snapshot, open in Visual Studio's Diagnostic Tools or dotnet-gcdump analysis.
Top retainer: Microsoft.EntityFrameworkCore.ChangeTracking.InternalEntityEntry, millions of them. Trace back: a singleton DbContext was injected into a hot-path service for "performance", every request adds tracked entities that never leave the graph until process death.
The 10-minute load test never ran long enough for the leak to manifest.

Fix: Add a soak-test stage to nightly CI that runs k6 at 100 requests per second for 4 hours and asserts heap stays bounded:

Pair with a sidecar that polls /metrics (Prometheus exporter) every minute and posts dotnet_total_memory_bytes to the test report; the test fails if working set grows > 50% across the run. Source-fix: scope the DbContext per request ( AddDbContext registers as Scoped by default, don't override).

Why it works: Load tests catch latency / throughput regressions because they overwhelm short-term resources. Soak tests catch slow accumulation, the production failure mode you only see at the time-scale of real traffic.
Memory growth on a steady requests per second is the canonical signal of a leak; flat is healthy regardless of absolute level.

That asserts the repository's Save was called, testing the implementation, not the behavior. If you refactor to use a different repository method ( SaveAsync, Add + SaveChanges, et cetera) the test breaks even though behavior is identical.
Better: assert observable outcomes, "after ProcessOrder, calling GetOrder(id) returns the persisted order with status Submitted." That uses an in-memory fake repository and verifies through the same surface real callers use.
Mocks for verifying interactions are fine for side effects you can't observe directly (email sent, message published), not internal collaborator calls.

UseInMemoryDatabase ignores sequel provider behavior, no transactions, no row-version concurrency, no foreign-key constraints, no migrations, no provider-specific sequel (for example, LIKE collation, Jason functions, RAISERROR ).
Tests pass; production explodes on the first concurrent update or on a query that translated fine for sequel Server but blew up for Postgres.
Use Testcontainers with the actual target database for any test that exercises the data layer; reserve InMemory for cases where you genuinely don't care about persistence semantics (rare).

At 100 requests per second, p99 means roughly 1 request per second feels broken. Over a 5-minute session a typical user hits ~50 endpoints; statistical likelihood of seeing at least one 2-second pause is high.
That's the difference between "this app feels fast" and "this app feels janky." Optimize for p99 first if customer-facing, tail latency dominates perceived performance once average is reasonable. Mean is a vanity metric.
